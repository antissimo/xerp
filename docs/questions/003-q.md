# Spec 003 — questions

## From the tester (acceptance tests, branch `tests/003-mcp-server`)

None of these blocked the tests. Each states what the tests do, so the architect only has to confirm or correct.

### T-Q1. AC-04 and AC-05 are not in the acceptance tests
Both are marked *(unit)* and can only be written against internal types that do not exist yet (the
`AppError` -> tool result mapper; the Application `get` operations). The tester role forbids tests through
internal types, so they are left to the builder in `tests/Xerp.UnitTests`. AC-03 *is* covered, by reflection
over the `Xerp.Api` assembly (namespace `Xerp.Api.Mcp` and below; it also fails when that namespace is empty).
Confirm that the builder owns AC-04 and AC-05.

### T-Q2. AC-42: must annotation values be explicit on the wire?
The table gives values that equal the MCP defaults in places (`idempotentHint: false` for `*_create`,
`destructiveHint: true` for `*_delete`). **Tested:** every cell that is not "—" must be present with exactly
that value; for the read-only tools only `readOnlyHint == true` and `openWorldHint == false` are asserted.
Is "absent, because it is the default" acceptable instead?

### T-Q3. R14 / E8 go further than AC-71
- E8 says `uom_list { "limit": "10" }` has `errors.limit`; AC-71 only asks for non-empty `errors`.
- R14 says `arguments` that is not an object is a `VALIDATION_FAILED` tool error; no criterion covers it, and
  the official client cannot send it (it would need a raw JSON-RPC request).

**Tested:** exactly what AC-71 says (non-empty `errors`); the non-object `arguments` case is not tested.
Should a criterion be added for either?

### T-Q4. Readings the tests take where the criterion leaves room
- AC-16: `GET /api-keys/{id}` has **exactly** the eight properties of section 4 (`id`, `name`, `actorType`,
  `isActive`, `createdAt`, `createdBy`, `revokedAt`, `revokedBy`), each equal to the `201` body.
- AC-20: the second revocation is sent by a *different* key than the first, so that R6 ("`revokedBy` keeps its
  first value") is actually observable.
- AC-25: the losing request must be a `401 UNAUTHENTICATED` problem with `WWW-Authenticate: Bearer`.
- AC-33: the allow-list is configured as `Xerp:Mcp:AllowedOrigins:0`; on that host a non-listed `Origin` is
  still `403` and a request without `Origin` is processed (S2).
- AC-35: the SDK does not promise an exception type, so the test asserts that the call throws (no tool
  result), that any `HttpRequestException` in the chain carries `401`, and that a raw `tools/call` with the
  revoked key is a `401 UNAUTHENTICATED` problem.
- AC-36: status `< 500` and not `404` (a `404` would only prove that `/mcp` is not mapped).
- AC-41: a tool without arguments or without required arguments may omit `properties` / `required` or send
  them empty; `additionalProperties: false` must be present on every tool.
- AC-44: also compares `instructions` between tenants and checks that neither contains tenant data (T6).
- AC-45: also tries `tenant_create` (E6).

### T-Q5. For the builder: SDK version used by the tests
The test project references `ModelContextProtocol` **2.2.0** (`Directory.Packages.props`). The client helper
(`tests/Xerp.IntegrationTests/Support/McpSupport.cs`) was smoke-tested against a throwaway stateless server
built with `ModelContextProtocol.AspNetCore` 2.2.0 (`WithHttpTransport(o => o.Stateless = true)`): it connects
without a session id, `GET`/`DELETE` give `405`, an unknown tool surfaces as `McpProtocolException`, and
`not json` gives `400`. With that pair the negotiated revision was `2026-07-28`. Note that the SDK's generated
input schema has no `additionalProperties: false` and that its default capabilities also contained `logging`.

## Answers (architect, 2026-10-09)

### T-Q1 — confirmed
The builder owns AC-04 and AC-05; spec 003 §10 now marks them *(builder)*, together with AC-03 and AC-12
("Who tests what"). Your reflection test for AC-03 uses no internal type and may stay; the builder need not
duplicate it. AC-12 reads the database, so it is the builder's; if you already wrote it, it may stay as well.

### T-Q2 — explicit, as tested
Every cell of the annotation table that is not "—" is sent explicitly with that value, also where it equals
the MCP default. A reader of `tools/list` (a model, usually) should not need to know the protocol's defaults,
two of which (`destructiveHint: true`, `openWorldHint: true`) are the unsafe reading. "Absent because default"
is not acceptable. Spec 003 §5.3 now says so; AC-42 is unchanged and your test is right.

### T-Q3 — AC-71 tightened; the non-object case is dropped
- Wrong JSON type and unknown argument: the `errors` key is the argument's name, exactly as over HTTP
  (001/E4: `errors.name`, `errors.foo`). AC-71 now asks for it: `"name": 123` -> key `name`;
  `{ "limit": "10" }` -> key `limit`; unknown `tenantId` / `foo` -> key `tenantId` / `foo`. Please tighten the
  test accordingly.
- `arguments` that is not an object: removed from R14 as a requirement. No conforming client sends it; the only
  rule left is the general one (never HTTP `500`, never `INTERNAL_ERROR`), and no criterion is added. This
  follows the owner's guidance of 2026-10-09 to keep protocol edge cases to what is already established.

### T-Q4 — all nine readings confirmed
They are what the criteria mean. Two remarks:
- AC-41: a tool with no arguments may omit `properties` / `required` or send them empty — confirmed;
  `additionalProperties: false` on every tool is mandatory.
- AC-20 with a different key for the second revocation is the better test; AC-20 now says so.

### T-Q5 — noted, with two consequences for the builder
- SDK 2.2.0 for client and server; the negotiated revision `2026-07-28` satisfies AC-30 (`>= 2025-06-18`).
  ADR-0009 now records these as verified facts.
- The SDK's generated input schema lacks `additionalProperties: false`: the builder must add it (AC-41) and
  must reject unknown arguments as a tool error (AC-71) — the schema alone enforces nothing.
- The SDK's default capabilities contain `logging`. That is acceptable: AC-30 requires `tools` and forbids
  `resources` and `prompts`; it says nothing about `logging`, and the server is not required to remove it.
  The server sends no log notifications (stateless, no stream).
