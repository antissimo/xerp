## From the builder (implementation, branch `feat/011-default-warehouse-stock-balance`)

### B-Q1. DISPUTED — six acceptance tests read `createdBy` / `updatedBy` as an object (not changed by the builder; they fail)
`createdBy` and `updatedBy` are UUID strings in every representation (architecture §8; 004 §4.2), and the tester's
own `DefaultWarehouseTests` reads them so (`GetProperty("createdBy").GetGuid()`). Six tests of this spec instead
call the helper `.Id()` on them, which is `GetProperty("id").GetGuid()` — for a record, not for an id — and throw
`InvalidOperationException: The requested operation requires an element of type 'Object', but the target element
has type 'String'` before they reach their remaining assertions:

| Test | Lines |
|---|---|
| `McpDefaultWarehouseBalanceToolTests.AC71_Default_warehouse_stock_list_verify_and_rebuild_through_tools_only` | 71 (`draft.createdBy`), 105 (`made.updatedBy`), 110 (`former.updatedBy`) |
| `McpDefaultWarehouseBalanceToolTests.AC72_An_order_created_through_a_tool_without_warehouseId_is_on_the_default_warehouse` (4 rows) | 169 (`created.createdBy`) |
| `DefaultWarehouseBalanceIsolationTests.AC80_Each_tenant_has_its_own_default_and_the_others_does_not_exist` | 46, 47 (`xDefault.createdBy`, `yDefault.createdBy`) |

**Asked:** replace `.Id()` by `.GetGuid()` on these six lines. Checked locally and reverted (the committed files
are the tester's, byte for byte): with exactly that change all six tests pass against this branch, every other
assertion in them included. Making them pass as written would mean returning `createdBy` as an object, which
breaks the contract and some two hundred other tests.

### B-Q2. AC-01 and two earlier *builder* tests that write the ledger behind Application
`StockReversalImmutabilityTests` (spec 006, AC-02 *(builder)*) has two tests that add ledger entries through
the `DbContext` directly — a reversal built in the test, without `StockDocumentOperations` — and then assert
stock on hand. Since R23 stock on hand is the stored balance, and by R21 / ADR-0018 decision 3 only
Application's posting writes it, so after such a write the balance of that pair is behind the ledger: exactly
the defect verify exists to find. AC-01 lists the only earlier tests that may change and says none that
asserts a quantity does; these two are not on the list.

**Done:** both tests now call `POST /stock-balances/rebuild` (asserting one difference, `corrected == 1`)
before reading stock; every quantity they assert is the one asserted before (0 and 100). Nothing else in
them changed. The alternative — the `DbContext` writing balances for every added ledger entry on save — would
make them pass untouched, but it is the trigger ADR-0018 rejects ("one writer in Application"). Say so if
that is preferred after all, or if the two tests should assert something else.

### B-Q4. Rebuild writes only the rows that differ
R25 says rebuild "replaces the stored balances … by the sums of the ledger". As built it finds the differing
pairs with the one statement verify uses (set-based, in the database) and writes only those rows — in a
healthy tenant it writes nothing; a row whose pair has no ledger entries at all is deleted (no row means 0,
§3). The outcome is the same as a full replacement, `corrected` falls out of it, and every corrected pair is
logged (S5). It also keeps the single writer in Application (AC-05) instead of a second one in SQL.
The migration, which has no Application, does the full `INSERT … SELECT SUM … GROUP BY`.

### B-Q5. Smaller choices, for confirmation
- **Lock on warehouse writes.** `PUT`, `DELETE` and `set-default` of a warehouse all run under the per-tenant
  lock (§11 allowed the lock or row locks); `POST /warehouses` takes none. A warehouse `PUT` therefore waits
  for a posting of the same tenant in progress.
- **Unknown `type` on create without `warehouseId`** → only `type` is reported, not `warehouseId` (whether the
  warehouse may be omitted depends on the type).
- **A body sent to `POST /stock-balances/rebuild`** is not read: `200` (T-Q3 allowed `200` or `400`).
- **Migration, a tenant without any API key** cannot get a warehouse (`CreatedBy` is a mandatory reference) and
  is skipped. Such a tenant cannot exist through the API — a tenant is created with a key and keys are never
  deleted — so R29 holds for every real tenant.
- **Migration, zero sums.** A pair whose ledger sums to 0 gets a row with 0 (§3 leaves that open).
- **Verify** reads `total` and the page inside one `REPEATABLE READ` transaction (a new port,
  `IXerpDb.AtOneMomentAsync`), and the comparison itself is one statement.
- **`docs/architecture.md` §6** does not list `DEFAULT_WAREHOUSE` yet, and §5 / §8 still say stock on hand "is
  the sum of the ledger"; `docs/getting-started.md` may still tell a new tenant to create a warehouse first.
  Not the builder's files.
