per document; the ledger's `total` must be exactly that many entries.

## Answers from the architect to the tester (2026-10-10)

Every reading is confirmed. **No answer changes a test.** Four answers amend the spec in words (T-Q1, T-Q2,
T-Q3, T-Q4); none of them changes a rule.

### T-Q1
Confirmed, all of it. `McpPartnerWarehouseToolTests` and `PartnerWarehouseIsolationTests` are "their like" of
item 3: they change by exactly the default warehouse and their requests are unchanged. The count in the spec
008 test that repeats the literal list belongs to item 1; AC-01 now says so.

### T-Q2
Confirmed: **equal**. "`updatedAt` / `updatedBy` of the call" is one timestamp and one key — the two
warehouses change in one transaction and are stamped once. R6 and AC-25 now say that the two `updatedAt`
values are equal. Two timestamps taken within one call are not acceptable.

### T-Q3
- Query parameters: confirmed. 001/R15 holds on every `/api/v1` route, the ones that define no parameter
  included; AC-11 now names the two `POST` routes.
- A body sent to rebuild: an operation specified as "(no body)" does not read a body (`003-q.md`: revoke
  "ignores a request body if one is sent"; the same holds for post, confirm, close and reopen as built). So
  the answer is `200` and nothing in the body has any effect — which is all S2 needs: the balance is not an
  input. Section 4.5 now says so for set-default and rebuild. Your assertion (`200` or `400`, no balance
  changed) is wider than that and stays as it is.

### T-Q4
All five keys confirmed: a tool argument that the HTTP operation would reject as an unknown query parameter
or body property is `VALIDATION_FAILED` under the argument's own name (spec 003), so the tool key equals the
HTTP key. AC-73 now names `foo` and `tenantId`. A call without `id`: `VALIDATION_FAILED` with non-empty
errors is enough to assert.

### T-Q5
Confirmed, per type:
- receipt: always `200` — nothing a parallel posting does can refuse a receipt into an active warehouse;
- issue, transfer: `200` or `INSUFFICIENT_STOCK`;
- count: `200` or `COUNT_OUTDATED`;
- reversal of a receipt: `201`, `INSUFFICIENT_STOCK`, or `INVALID_STATE` (the same original reversed twice).
Computing the expected quantity from the opening ledger plus the entries read per succeeded document, and
requiring the ledger's `total` to be exactly that many entries, is the right reading of "the sum computed by
the test": a count without a difference contributes no entry (E14), and reading per document accounts for it.

### T-Q6
All six confirmed against the rules:
- AC-44: a deleted article is not an article of the tenant (R13); it leaves every stock list. Only an unused
  article can be deleted, so no quantity ever disappears this way.
- AC-45: `search` is the article's `code` or `name` only (R15, 002/R18) — never the warehouse or the unit.
- AC-42 / E13: `hasStock` looks at `quantity` alone; an incoming or reserved quantity does not make it true.
- AC-50: after the reversal of the delivery the order is still confirmed and its whole quantity is
  outstanding, so it is reserved again (010/R14, R15). `reservedQuantity == 30` is right.
- AC-54: posting a receipt and an issue after the rebuild and expecting the next number of each series is
  the black-box form of "the next document numbers are as before".
- AC-58: gapless per series over posted and reversed documents is right (a reversing document takes its
  number from the series of its type, ADR-0013).

### T-Q7
Confirmed. The non-empty difference list, `corrected > 0` and the content of the difference item are the
builder's (AC-03); section 11 says black-box verify is only ever seen empty.

## From the builder (implementation, branch `feat/011-default-warehouse-stock-balance`)

### B-Q1. DISPUTED — six acceptance tests read `createdBy` / `updatedBy` as an object (not changed by the builder; they fail)
`createdBy` and `updatedBy` are UUID strings in every representation (architecture §8; 004 §4.2), and the tester's
own `DefaultWarehouseTests` reads them so (`GetProperty("createdBy").GetGuid()`). Six tests of this spec instead
call the helper `.Id()` on them, which is `GetProperty("id").GetGuid()` — for a record, not for an id — and throw
`InvalidOperationException: The requested operation requires an element of type 'Object', but the target element
has type 'String'` before they reach their remaining assertions:

| Test | Lines |
|---|---|
| `McpDefaultWarehouseBalanceToolTests.AC71_Default_warehouse_stock_list_verify_and_rebuild_through_tools_only` | 71 (`draft.createdBy`), 105 (`made.updatedBy`), 110 (`former.updatedBy`) |
| `McpDefaultWarehouseBalanceToolTests.AC72_An_order_created_through_a_tool_without_warehouseId_is_on_the_default_warehouse` (4 rows) | 169 (`created.createdBy`) |
| `DefaultWarehouseBalanceIsolationTests.AC80_Each_tenant_has_its_own_default_and_the_others_does_not_exist` | 46, 47 (`xDefault.createdBy`, `yDefault.createdBy`) |

**Asked:** replace `.Id()` by `.GetGuid()` on these six lines. Checked locally and reverted (the committed files
are the tester's, byte for byte): with exactly that change all six tests pass against this branch, every other
assertion in them included. Making them pass as written would mean returning `createdBy` as an object, which
breaks the contract and some two hundred other tests.

### B-Q2. AC-01 and two earlier *builder* tests that write the ledger behind Application
`StockReversalImmutabilityTests` (spec 006, AC-02 *(builder)*) has two tests that add ledger entries through
the `DbContext` directly — a reversal built in the test, without `StockDocumentOperations` — and then assert
stock on hand. Since R23 stock on hand is the stored balance, and by R21 / ADR-0018 decision 3 only
Application's posting writes it, so after such a write the balance of that pair is behind the ledger: exactly
the defect verify exists to find. AC-01 lists the only earlier tests that may change and says none that
asserts a quantity does; these two are not on the list.

**Done:** both tests now call `POST /stock-balances/rebuild` (asserting one difference, `corrected == 1`)
before reading stock; every quantity they assert is the one asserted before (0 and 100). Nothing else in
them changed. The alternative — the `DbContext` writing balances for every added ledger entry on save — would
make them pass untouched, but it is the trigger ADR-0018 rejects ("one writer in Application"). Say so if
that is preferred after all, or if the two tests should assert something else.

### B-Q3. AC-01 item 5 and one earlier builder unit test
`StockDocumentValidationTests.R3_Warehouse_id_is_required_and_a_uuid` (builder, spec 005) asserted `400` for a
create without `warehouseId` — the unit-level twin of 005/AC-26, which item 4 moves to AC-30. It now asserts
that the omission is accepted and reported as omitted, and that `"abc"` and `""` are still invalid. Item 5
names only the unit tests of tenant provisioning; there were none (two are added). Recorded because the
literal list of AC-01 does not cover it.

### B-Q4. Rebuild writes only the rows that differ
R25 says rebuild "replaces the stored balances … by the sums of the ledger". As built it finds the differing
pairs with the one statement verify uses (set-based, in the database) and writes only those rows — in a
healthy tenant it writes nothing; a row whose pair has no ledger entries at all is deleted (no row means 0,
§3). The outcome is the same as a full replacement, `corrected` falls out of it, and every corrected pair is
logged (S5). It also keeps the single writer in Application (AC-05) instead of a second one in SQL.
The migration, which has no Application, does the full `INSERT … SELECT SUM … GROUP BY`.

### B-Q5. Smaller choices, for confirmation
- **Lock on warehouse writes.** `PUT`, `DELETE` and `set-default` of a warehouse all run under the per-tenant
  lock (§11 allowed the lock or row locks); `POST /warehouses` takes none. A warehouse `PUT` therefore waits
  for a posting of the same tenant in progress.
- **Unknown `type` on create without `warehouseId`** → only `type` is reported, not `warehouseId` (whether the
  warehouse may be omitted depends on the type).
- **A body sent to `POST /stock-balances/rebuild`** is not read: `200` (T-Q3 allowed `200` or `400`).
- **Migration, a tenant without any API key** cannot get a warehouse (`CreatedBy` is a mandatory reference) and
  is skipped. Such a tenant cannot exist through the API — a tenant is created with a key and keys are never
  deleted — so R29 holds for every real tenant.
- **Migration, zero sums.** A pair whose ledger sums to 0 gets a row with 0 (§3 leaves that open).
- **Verify** reads `total` and the page inside one `REPEATABLE READ` transaction (a new port,
  `IXerpDb.AtOneMomentAsync`), and the comparison itself is one statement.
- **`docs/architecture.md` §6** does not list `DEFAULT_WAREHOUSE` yet, and §5 / §8 still say stock on hand "is
  the sum of the ledger"; `docs/getting-started.md` may still tell a new tenant to create a warehouse first.
  Not the builder's files.

## Answers from the architect to the builder (2026-10-10, with review 011)

### B-Q1 — upheld
The builder is right and the code stays. `createdBy` and `updatedBy` are UUID strings in every representation
(architecture §8; 004 §4.2; AC-20 and AC-25 of this spec compare them with a key's id). `.Id()` reads the
property `id` of an object. The six lines are a defect of the tests, not raised as a question, so my answer
above ("no answer changes a test") did not cover it. Required change 1 of review 011, for the **tester**:
`.GetGuid()` in place of `.Id()` on

- `McpDefaultWarehouseBalanceToolTests`, lines 71, 105, 110 (`AC71_…`) and 169 (`AC72_…`, four rows);
- `DefaultWarehouseBalanceIsolationTests`, lines 46 and 47 (`AC80_…`).

Nothing else in those tests changes. The builder changes no code and no tester file.

### B-Q2 — accepted as done
The two tests write ledger entries behind Application, which since this spec is by definition the defect
verify finds; the rebuild before the read is the honest form, and it adds an assertion (one difference,
`corrected == 1`) without weakening one — the quantities asserted are those of before. A `DbContext` that
writes balances for every added entry is the trigger ADR-0018 rejects; not wanted. AC-01 has a new item 6
that names this change.

### B-Q3 — accepted as done
The unit-level twin of 005/AC-26 moves with it. AC-01 item 4 now names the builder's unit tests of the same
case; item 5 stays for the provisioning tests (the two added ones).

### B-Q4 — accepted
"Replaces by the sums of the ledger" describes the outcome, not the statement. Finding the differing pairs
in the database and writing only those through the one writer gives the same balances, the right `corrected`
and nothing written in a healthy tenant. R25 now says "makes equal to". One remark, non-blocking 2 of the
review: a pair whose ledger sum is negative makes `CorrectTo` throw.

### B-Q5 — all confirmed
- The lock on warehouse `PUT`, `DELETE` and set-default: confirmed (§11 allowed it). Open item 005/5
  ("deactivating a warehouse takes no lock") is superseded and updated.
- Unknown `type` without `warehouseId` -> only `type`: confirmed; whether the warehouse may be omitted
  cannot be said without the type.
- A body sent to rebuild is not read, `200`: this is what section 4.5 now specifies (T-Q3).
- Migration, a tenant without any key is skipped: accepted; such a tenant cannot exist through the API and
  cannot call it. R29 now says so.
- Migration, a zero sum gets a row with 0: fine (§3 leaves it open; stock on hand does not list it).
- Verify in one `REPEATABLE READ` transaction with the comparison in one statement: this is what §11 asked.
- Docs: `DEFAULT_WAREHOUSE` has been in architecture §6 on `main` since the spec was written (the branch
  was cut earlier). §8 said "stock on hand is the sum of the stock ledger" one bullet above the projection
  rule: corrected. `docs/getting-started.md` now says a new tenant already has a warehouse.
