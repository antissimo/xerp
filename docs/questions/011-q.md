### T-Q2. R6 / AC-25: `updatedAt` of the two warehouses
**Tested:** after `set-default` of W1 the former default and W1 have the **same** `updatedAt` (the "`updatedAt`
/ `updatedBy` of the call"), later than the former default's old one, and nothing else about either changed.
If two timestamps taken within one call are acceptable, the equality has to go.

### T-Q3. AC-11: query parameters on the two `POST` routes, a body on rebuild
**Tested:** `POST /warehouses/{id}/set-default?foo=1` and `POST /stock-balances/rebuild?tenantId=…` -> `400`
with that key (the inherited rule for unknown query parameters). A JSON **body** sent to rebuild
(`{ articleId, warehouseId, quantity }`) is tested only for its effect: `200` or `400`, and no balance changes
(S2). Say so if one of the two statuses is required.

### T-Q4. AC-73: keys of the tool errors
**Tested:** `warehouse_stock_list { id, foo }` -> `VALIDATION_FAILED` with key `foo`, the same key as
`GET …/stock?foo=1`; `stock_balance_difference_list { warehouseId }` -> key `warehouseId`;
`stock_balance_rebuild { tenantId }` -> key `tenantId`; `warehouse_create { …, isDefault }` -> key `isDefault`;
`hasStock: "yes"` -> key `hasStock`. A call without `id` is only asserted as `VALIDATION_FAILED` with errors.

### T-Q5. AC-56: the codes a type allows
**Tested:** a receipt never conflicts (always `200`); an issue and a transfer may be `INSUFFICIENT_STOCK`; a
count `COUNT_OUTDATED`; a reversal `INSUFFICIENT_STOCK` or `INVALID_STATE`. The race has 34 requests (6 + 4
receipts, 6 issues, 5 + 5 transfers, 4 counts of B, 4 reversals of receipts of 10 that make up the 1000 of A).
The expected quantity per pair is the opening ledger plus the entries of the documents that succeeded, read
per document; the ledger's `total` must be exactly that many entries.

### T-Q6. Beyond the letter of the criteria
- AC-44: a deleted (unused) stock article leaves every stock list.
- AC-45: `search` matches the article's code or name only — `search=W1` and `search=pcs` are empty.

## Answers from the architect to the tester (2026-10-10)

Every reading is confirmed. **No answer changes a test.** Four answers amend the spec in words (T-Q1, T-Q2,
T-Q3, T-Q4); none of them changes a rule.

### T-Q1
Confirmed, all of it. `McpPartnerWarehouseToolTests` and `PartnerWarehouseIsolationTests` are "their like" of
item 3: they change by exactly the default warehouse and their requests are unchanged. The count in the spec
008 test that repeats the literal list belongs to item 1; AC-01 now says so.

### T-Q2
Confirmed: **equal**. "`updatedAt` / `updatedBy` of the call" is one timestamp and one key — the two
warehouses change in one transaction and are stamped once. R6 and AC-25 now say that the two `updatedAt`
values are equal. Two timestamps taken within one call are not acceptable.

### T-Q3
- Query parameters: confirmed. 001/R15 holds on every `/api/v1` route, the ones that define no parameter
  included; AC-11 now names the two `POST` routes.
- A body sent to rebuild: an operation specified as "(no body)" does not read a body (`003-q.md`: revoke
  "ignores a request body if one is sent"; the same holds for post, confirm, close and reopen as built). So
  the answer is `200` and nothing in the body has any effect — which is all S2 needs: the balance is not an
  input. Section 4.5 now says so for set-default and rebuild. Your assertion (`200` or `400`, no balance
  changed) is wider than that and stays as it is.

### T-Q4
All five keys confirmed: a tool argument that the HTTP operation would reject as an unknown query parameter
or body property is `VALIDATION_FAILED` under the argument's own name (spec 003), so the tool key equals the
HTTP key. AC-73 now names `foo` and `tenantId`. A call without `id`: `VALIDATION_FAILED` with non-empty
errors is enough to assert.

### T-Q5
Confirmed, per type:
- receipt: always `200` — nothing a parallel posting does can refuse a receipt into an active warehouse;
- issue, transfer: `200` or `INSUFFICIENT_STOCK`;
- count: `200` or `COUNT_OUTDATED`;
- reversal of a receipt: `201`, `INSUFFICIENT_STOCK`, or `INVALID_STATE` (the same original reversed twice).
Computing the expected quantity from the opening ledger plus the entries read per succeeded document, and
requiring the ledger's `total` to be exactly that many entries, is the right reading of "the sum computed by
the test": a count without a difference contributes no entry (E14), and reading per document accounts for it.

### T-Q6
All six confirmed against the rules:
- AC-44: a deleted article is not an article of the tenant (R13); it leaves every stock list. Only an unused
  article can be deleted, so no quantity ever disappears this way.
- AC-45: `search` is the article's `code` or `name` only (R15, 002/R18) — never the warehouse or the unit.
- AC-42 / E13: `hasStock` looks at `quantity` alone; an incoming or reserved quantity does not make it true.
- AC-50: after the reversal of the delivery the order is still confirmed and its whole quantity is
  outstanding, so it is reserved again (010/R14, R15). `reservedQuantity == 30` is right.
- AC-54: posting a receipt and an issue after the rebuild and expecting the next number of each series is
  the black-box form of "the next document numbers are as before".
- AC-58: gapless per series over posted and reversed documents is right (a reversing document takes its
  number from the series of its type, ADR-0013).

### T-Q7
Confirmed. The non-empty difference list, `corrected > 0` and the content of the difference item are the
builder's (AC-03); section 11 says black-box verify is only ever seen empty.
