# Spec 002 — questions from the builder

None of these blocked the implementation. Each states what was built, so the architect only has to confirm or
correct it.

## Q1. Two spec 001 tests had to change (AC-01 says none may be weakened)
Neither was weakened, but both were edited, because they pinned facts that spec 002 changes on purpose:
- `StructureTests.AC06_Database_has_exactly_the_tables_of_spec_001…` pinned the exact table list. It now expects
  `Articles` as well and was renamed `…exactly_the_specified_tables…`. (This is an extra test next to the model
  test of 001/AC-06; the model test itself is unmodified, as AC-03 requires.)
- `ErrorModelTests.AC71_Unknown_path_under_api_v1…` used `/api/v1/articles` as an example of an unknown path.
  That case is now `/api/v1/partners`. Spec 004 will have to move it again; consider a path no spec will claim.

## Q2. `ON DELETE RESTRICT` is reported by PostgreSQL as 23001, not 23503
AC-06 says a raw `DELETE` of a referenced unit "fails with a foreign-key violation". With the key declared
`ON DELETE RESTRICT`, PostgreSQL 18 raises SQLSTATE `23001` (`restrict_violation`), and `23503`
(`foreign_key_violation`) only for `NO ACTION` keys and for a missing target on insert/update.
**Built:** the keys are `RESTRICT`; the AC-06 test accepts either code and also asserts the constraint name;
Infrastructure translates both (`23001` -> blocked delete; `23503` -> blocked delete or missing reference,
depending on what was being saved). Confirm that `23001` counts as "a foreign-key violation" for AC-06.

## Q3. Accepted spellings of a UUID in `baseUnitId`
R5 says "a UUID string". **Built:** whatever .NET `Guid.TryParse` accepts, which is the same set the route
constraint `{id:guid}` already accepts for path ids: the canonical hyphenated form, and also 32 hex digits
without hyphens and the braced/parenthesised forms. Should request fields (and path ids) accept only the
canonical form?
Also: the all-zero UUID is well-formed, so it gives `409 REFERENCE_NOT_FOUND`, not `400`.

## Q4. Audit foreign keys on `Articles`
Same construction as spec 001 (001-q.md, Q2): `(TenantId, CreatedBy)` and `(TenantId, UpdatedBy)` ->
`ApiKeys (TenantId, Id)`, restrict. It is consistent with ADR-0010 ("keys are never deleted"). The AC-04 model
test covers these keys too, since `ApiKey` is tenant-owned.

## Q5. Details the spec leaves open (built as follows)
- `IN_USE` `detail` states the number of referencing articles (S3 allows it) on the ordinary path; when the
  database refuses a delete that raced with a new reference, the detail gives no number.
- `REFERENCE_NOT_FOUND` / `REFERENCE_INACTIVE`: `detail` names the request field only; the id is echoed in
  `errors.baseUnitId[0]`. For another tenant's unit the body is byte-identical to a random id's, id aside.
- List filters `type=` and `baseUnitId=` with an empty value are treated as absent, like the other parameters.
- After a successful create/replace the response is built from the saved article plus one read of the unit's
  code and name (two statements, not one join) — the unit cannot disappear once the article holds it.
- AC-10, AC-11 and AC-57 passed before any article code existed, because spec 001 guards `/api/v1` by path and
  answers unknown routes with `NOT_FOUND`. They are kept as regression tests.
