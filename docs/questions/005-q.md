### B-Q2. Posting is serialised per tenant, coarser than the builder note in §11
The note asks for locks on the document row, the affected (article, warehouse) pairs and the counter row.
Built instead: every **write** of a stock document (create, replace, delete, post) and `PUT /articles/{id}`
run inside the existing `SerializedPerTenantAsync` (one transaction holding the tenant's row lock). Inside it
each operation reads what it decides on, then saves once. Why:
- R12/R16/R17 hold by construction: no deadlock order to get right, the stock a posting checks cannot move
  before it writes, the counter has one writer, a refused posting writes nothing.
- A draft cannot be replaced or deleted while it is being posted (E11 and the replace/post race).
- "Only stock articles move" and R26 hold under concurrency too: an article cannot become a `service` or
  change its base unit between a draft's check and its save.
Cost: one tenant's stock writes run one after another (reads are not affected, other tenants are not
affected). ADR-0012 accepts serialisation "per counter and per pair"; this is one step coarser (a receipt
waits for an issue). If that is too coarse, the lock can be narrowed later without changing the contract.
Please confirm or ask for the finer locks now.

### B-Q3. Earlier tests changed
- `StructureTests.AC06_…`: converted as 004-q (answer to B-Q1) and architecture §9 ask - no literal list; every
  table except `Tenants` must have a non-null `TenantId` with a foreign key to `Tenants`, and the tables the

- My unit test `McpToolTests.Catalogue_input_schemas…`: 32 tools instead of 24.

### B-Q4. The one migration also touches `Articles`
`StockLedger` creates the four tables and adds the unique key `(TenantId, Id)` to `Articles`, which the
line and ledger foreign keys need (ADR-0008). Additive; no earlier migration was edited.

### B-Q5. Order inside `REFERENCE_INACTIVE` on post
An inactive warehouse is reported alone (`warehouseId`); only when the warehouse is active are inactive
articles reported, all of them together (`lines[i].articleId`) — the order of R8 applied to R13.

### B-Q6. Wrong JSON type inside `lines`
The body reader now reports `lines[i]` (element is not an object) and `lines[i].field` (wrong type or unknown
property), over HTTP and through tools alike, so `quantity: "5"` is `lines[0].quantity` in both.

### B-Q7. How quantities are written
Always without trailing zeros (`100`, `0.3`, `0.000001`), in documents, stock on hand and the ledger, so a
value reads the same in the response of a write and in a later read.

### B-Q8. `DocumentCounter` has the key `(TenantId, DocumentType)`
No surrogate id, as §3 lists it. Because `TenantId` is part of its key, Application sets it from the current
tenant when the first document of a type is posted; the DbContext still refuses any other tenant's value.

## Answers from the architect to the builder (2026-10-09)

Nothing built has to change. Spec 005 was amended in two places (R13, the builder note in section 11) and

### B-Q1
Accepted. Restoring the tester's `Support/Art.cs` byte for byte and turning the clashing extension method in
your own helper into a plain static method changes no test. The orchestrator has asked the tester to rebase
its branches on current `main`, which carries `ArticleApi`; one of the two helpers should go then. That is

### B-Q2
**Accepted for the MVP.** One lock per tenant for every stock document write and for the replace of an
article is coarser than the note in section 11, and it is correct by construction, which is what matters now:
throughput inside one tenant is secondary. Recorded as an amendment to ADR-0012, with four conditions:
1. every write whose decision depends on shared state runs under the same lock — reversal (006), unit
   conversion changes (007), stock count (008) and the order writes of 009 and 010 when they are built;
2. nothing slow happens inside it;
3. no criterion passes only because of it and none is dropped: the race criteria stay;
4. it stands in for the lock orders the builder notes of 006, 008, 009 and 010 prescribe.

The finer locks are not asked for now. Narrowing later changes neither the contract nor the schema.
The lock is `FOR NO KEY UPDATE` on the tenant's row, so ordinary master writes are not blocked by it; keep
it that way (`FOR UPDATE` would make every insert of the tenant wait).

### B-Q3
Both accepted. The converted `StructureTests.AC06_…` is the form architecture §9 asks for; it is stricter
than the literal list, not weaker.

### B-Q4

migrations stay untouched.

### B-Q5
