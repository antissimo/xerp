### T-Q3. R6: order of checks on Set, as tested
- random article + factor `0` -> `400` (validation before `404`);
- random article + random unit -> `404`;
- A + random unit + factor `0` -> `400`; A + base unit + factor `-1` -> `400`;
- A + its base unit **after that unit was deactivated** -> `UNIT_IS_BASE_UNIT` (not `REFERENCE_INACTIVE`).

### T-Q4. R9: the frozen base unit, as tested
On an article with a conversion and no stock documents: `baseUnitId` changed together with `name: ""` -> `400`;
on a random article id -> `404`; changed to a random UUID -> `IN_USE` with key `baseUnitId` (as 005-q T-Q3);
changed to the article's own alternative unit -> `IN_USE`. With two conversions, deleting one is not enough.

### T-Q5. R12: an inactive unit on a draft
`AC42_R12_…`: a draft has a line in `box`; `box` and `pack` are deactivated. A replace with two lines in `box`
-> `200` (not newly assigned); a replace that adds a line in `pack` -> `REFERENCE_INACTIVE` with exactly
`lines[1].unitId`; posting the draft afterwards -> `200` (R18).

### T-Q6. R16: order of kinds, as tested
- A random unit and a random article on different lines are reported together as `REFERENCE_NOT_FOUND`
  (`lines[0].unitId`, `lines[1].articleId`), although an inactive unit and a wrong unit are on other lines.
- A line of A with an **inactive unit that is not a unit of A** is `REFERENCE_INACTIVE`, not
  `UNIT_NOT_ON_ARTICLE`, and comes before `ARTICLE_NOT_STOCKED` of another line. Is that the intended reading —
  the unit's activity is checked without looking at the article?
- `ARTICLE_NOT_STOCKED` before `UNIT_NOT_ON_ARTICLE` before `QUANTITY_NOT_CONVERTIBLE`; validation before all.

### T-Q7. R17: what a draft shows
- `AC60_E7_…` asserts that a change of factor leaves the draft's `updatedAt` unchanged (the draft is converted
  when read, nothing is written to it). Drop the assertion if a write is allowed.
- AC-63: after the factor change the draft's line no longer converts. The tests read the draft and assert only
  `status`, `number` and the number of lines. What should `factor` and `baseQuantity` of such a line be on
  `GET` — the current factor and `0`?

### T-Q8. Readings the tests take where a criterion leaves room
- AC-20: `Location` is compared without regard to case; `tenantId` must be absent.
- AC-21: `createdAt` is compared as text between the three responses.
- AC-29 "the same property set as before": the eleven properties of spec 002, section 4, as a literal list.
- AC-41 is also posted: entries and stock equal those of a line without `unitId` (E5).
- AC-62: the reversing document's `lines` are compared with the original's as whole JSON values.
- AC-64: seven postings (receipt, issue, transfer, three factors changed, receipt, issue, reversal of the
  transfer, issue); stock equals the ledger after every one; final stock is asserted to the unit.
- AC-80: `article_unit_list` requires `articleId` only; `article_unit_set` requires all three and `factor`
  must be a JSON number; annotations follow the `read` / `update` / `delete` patterns. The text of the
  description of `article_unit_set` is not asserted (tests never assert on text).
- AC-82: `article_unit_list` with `limit: 0` -> `VALIDATION_FAILED` with key `limit`.
