### T-Q3. R6: order of checks on Set, as tested
- random article + factor `0` -> `400` (validation before `404`);
- random article + random unit -> `404`;
- A + random unit + factor `0` -> `400`; A + base unit + factor `-1` -> `400`;
- A + its base unit **after that unit was deactivated** -> `UNIT_IS_BASE_UNIT` (not `REFERENCE_INACTIVE`).

### T-Q4. R9: the frozen base unit, as tested
On an article with a conversion and no stock documents: `baseUnitId` changed together with `name: ""` -> `400`;
on a random article id -> `404`; changed to a random UUID -> `IN_USE` with key `baseUnitId` (as 005-q T-Q3);
changed to the article's own alternative unit -> `IN_USE`. With two conversions, deleting one is not enough.

### T-Q5. R12: an inactive unit on a draft

-> `200` (not newly assigned); a replace that adds a line in `pack` -> `REFERENCE_INACTIVE` with exactly

### T-Q6. R16: order of kinds, as tested
- A random unit and a random article on different lines are reported together as `REFERENCE_NOT_FOUND`
  (`lines[0].unitId`, `lines[1].articleId`), although an inactive unit and a wrong unit are on other lines.
- A line of A with an **inactive unit that is not a unit of A** is `REFERENCE_INACTIVE`, not
  `UNIT_NOT_ON_ARTICLE`, and comes before `ARTICLE_NOT_STOCKED` of another line. Is that the intended reading —
  the unit's activity is checked without looking at the article?
- `ARTICLE_NOT_STOCKED` before `UNIT_NOT_ON_ARTICLE` before `QUANTITY_NOT_CONVERTIBLE`; validation before all.

### B-D1. Dispute: one assertion of one tester test contradicts the spec

`McpArticleUnitToolTests.AC82_Addressing_arguments_are_validated_under_their_own_names`, line 176:

```csharp
await s.Mcp.ErrorAsync("article_unit_set", new { articleId = a, unitId = "abc", factor = 6 }, "VALIDATION_FAILED", "unitId");
```

The test expects `VALIDATION_FAILED` for a `unitId` that is a string but not a UUID. The spec says otherwise in
three places:
- Section 5: "`articleId` and `unitId` of these four tools are addressing arguments: 003/R15 applies to each
  under its own name". 003/R15: an addressing id that is "a string but not a UUID -> `NOT_FOUND`, as a malformed
  `{id}` path segment over HTTP"; only missing, `null`, empty or not a JSON string is `VALIDATION_FAILED`.
- AC-24: `PUT /articles/{A}/units/abc` -> `404` (and the tester's own `AC24_References_on_set` asserts that).
- AC-81 / AC-82: tool errors have "the same `code` ... as HTTP".

Built as the spec says: the tool answers `NOT_FOUND`, so **this test fails** on that assertion — the only
failing test of the suite. The other eleven assertions of the same test hold; they are repeated, together with
the `NOT_FOUND` reading, in the builder's `ItemUnitConversionBuilderTests.S5_Addressing_arguments_…`, which
passes. To decide: either the tester changes line 176 to `NOT_FOUND`, or the architect rules that `unitId` on
`article_unit_set` is a reference argument (then a malformed one is `VALIDATION_FAILED` on the tool while HTTP
stays `404`, and section 5 needs the exception written down).

### B-Q1. R12 / R16: an inactive unit that is not a unit of the line's article (tester's T-Q6)
Built as the tester reads it and as the order in R16 gives it: a given `unitId` is checked for being active
without asking whose unit it is, **except** when it is the base unit of that line's article — that one is
never checked (R12). So `REFERENCE_INACTIVE` comes before `ARTICLE_NOT_STOCKED` and `UNIT_NOT_ON_ARTICLE`, and
an inactive unit that is the base unit of *another* article is refused like any other inactive unit
(`AC42_R12_An_inactive_unit_that_is_another_articles_base_unit_is_still_refused`). The sentence
"`REFERENCE_INACTIVE` on a line's unit therefore concerns alternative units only" is read as "never the line's
own base unit", not as "only units that have a conversion on this article". Confirm or correct.

### B-Q2. R17 / E8: what a draft shows when a line no longer converts (tester's T-Q7)
`GET` shows the current `factor` and what the quantity converts to with it, also when that is not acceptable
for posting: `baseQuantity` is then `0` (or a value above 999999999.999999). Nothing is written to the draft
and `updatedAt` does not move. Posting such a draft is `QUANTITY_NOT_CONVERTIBLE`. Test:
`E8_A_draft_line_that_no_longer_converts_…`. The spec does not say what to show; a `0` in `baseQuantity` is
the only case where a representation carries a base quantity that 005/R6 would not accept.

### B-Q3. Smaller readings
- **R3, repeated Set.** A Set with the factor the conversion already has still stamps `updatedAt` /
  `updatedBy`: "who last set a factor" (S1) is the last caller. Say so if an unchanged factor must not count.
- **Section 3, "`Factor` and `BaseQuantity`, set at posting".** Both columns are `NULL` on a draft line and
  written once, by the posting (or copied by a reversal). The migration leaves them `NULL` on existing draft
  lines and sets `1` / `Quantity` on lines of posted and reversed documents (AC-03, tested on a database
  migrated from the state before this spec).
- **`ArticleUnits` has no id column**: its primary key is `(TenantId, ArticleId, UnitId)` (ADR-0014,
  decision 8). The table test passes; a later spec that wants to reference a conversion would need a key.
- **`DELETE /articles/{id}` now runs under the tenant lock** too (it deletes the article's conversions in the
  same save). Without it a Set of a new conversion racing with the delete could make the delete answer
  `IN_USE` for an article nothing uses. ADR-0012's amendment names stock document writes and
  `PUT /articles/{id}`; this adds one more holder of the same lock, nothing new to wait for.
- **Posting order.** As R18: masters active -> conversion -> stock; the counter is advanced after all three.

### B-Q4. A read can race with a write (not new in this spec)
`GET /stock-documents/{id}` reads the document and then the masters it shows in separate statements, outside
any lock. If, between the two, the draft is replaced and a master it named is deleted (now also: its line's
conversion), the read would look up a master that is gone and end as `500`. This is reasoned from the code,
not reproduced. The window existed since spec 005 for warehouses and articles; this spec adds conversions to
it. No acceptance criterion reaches it. A snapshot (`REPEATABLE READ`, read-only)
around document reads would close it for all three; that is a port on `IXerpDb` and so a question for the
architect rather than something to slip into this spec.

### B-Q6. For the reviewer: where the rules are
- One conversion function: `Xerp.Domain.Inventory.UnitConversion` (R2, R14, R15), unit-tested in
  `UnitConversionTests` (AC-02). Reading a draft, saving and posting all go through it.
- `StockDocument.Post` takes the factors, stores `Factor` / `BaseQuantity` on the lines and builds the ledger
  entries from the stored `BaseQuantity`; `StockDocument.Reverse` copies the posted lines and negates the
  original's entries — it is given nothing about conversions.
- The order of kinds on lines (R16) is `StockLineChecks.References`; the conversion check of saving and of
  posting is `StockLineChecks.Convert`. Both are pure and unit-tested in `StockUnitLineRulesTests`.
- Conversion writes (`ArticleUnitOperations.SetAsync` / `DeleteAsync`) run under
  `IXerpDb.SerializedPerTenantAsync`; `RecordAddress.Id` takes the argument's name.
