# Spec 009 — questions

## From the tester (acceptance tests, branch `tests/009-purchase-orders-goods-receipt`)

None of these blocked the tests. Each states what the tests do, so the architect only has to confirm or correct.
No criterion needed an internal type or a look into the database.

### T-Q1. Changes to earlier tests (AC-01)
Made on this branch only, all in `McpToolListTests`: the literal list (45 names, `Spec009Tools`); the pinned
properties of `stock_document_create` and `stock_document_list` (`purchaseOrderId`); the pinned properties of
a `lines` item of `stock_document_create` / `_update` (`orderLineNo`, integer or null); the count in the spec
008 test that repeats the literal list (37 -> 45). No earlier test asserted the exact property set of a stock
document, a summary, a line or a stock-on-hand item, so nothing else changed. The earlier helper
`Stock.AssertStockEqualsLedgerAsync` (it requires every listed pair to have a positive `quantity`) is
untouched; order tests use a new helper that compares the pairs whose `quantity` is not zero.

### T-Q2. How the tests are organised (for the builder and for spec 010)
The criteria about the order itself are written once, against `Support/OrderApi` (routes, tool names and the
names that differ between the two kinds of order), in abstract classes: `OrderDraftTests` (AC-10, 11, 20–28),
`OrderLifecycleTests` (AC-30–35, 63, 65), `OrderLinkTests` (AC-48–50, 54), `OrderMasterEffectsTests`
(AC-80–82), `OrderIsolationTests` (AC-90–93), `McpOrderToolTests` (AC-86–88). `PurchaseOrderTests.cs` runs
them for purchase orders. `PurchaseReceiptTests` (AC-40–47, 51–53, 55) and `PurchaseOrderProgressTests`
(AC-60–62, 64, 70–72, 75–77) are purchase-only. On `tests/010-…` the same abstract classes get a second
concrete class each; nothing in them changes.

### T-Q3. The key of an unknown body property
AC-50 / R19: `purchaseOrderId` in a replace body -> `400`. AC-11 / E4: `status`, `number`, `totalAmount`,
`tenantId`, a line with `lineNo`. **Tested:** `400 VALIDATION_FAILED` with a non-empty `errors`, no particular
key (as the tests of spec 005 do).

### T-Q4. Words asserted in tool descriptions (AC-85, section 5 "Descriptions say")
Only identifiers an agent has to act on, never prose: `stock_document_post` contains `ORDER_NOT_OPEN`,
`QUANTITY_EXCEEDS_ORDER`, `outstandingBaseQuantity`; `purchase_order_get` contains `receipt`,
`purchaseOrderId`, `orderLineNo`, `outstandingBaseQuantity`; `purchase_order_create` contains `unitPrice`,
`isSupplier`, `PARTNER_ROLE_MISSING`; `purchase_order_confirm` contains `INVALID_STATE` (003 §5.3: a
description names its error codes). The `*_delete` descriptions of the masters are not asserted.

### T-Q5. R12: order of checks at confirmation, as tested
One draft whose supplier is inactive **and** without the role, whose warehouse is inactive, whose first
article is inactive and whose second line no longer converts is confirmed six times:
`REFERENCE_INACTIVE` {`supplierId`, `warehouseId`} -> (supplier reactivated) {`warehouseId`} -> {`lines[0].articleId`}
-> `PARTNER_ROLE_MISSING` {`supplierId`} -> `QUANTITY_NOT_CONVERTIBLE` {`lines[1].quantity`} -> `200`,
`PO-000001`. In each step `errors` has exactly those keys.

### T-Q6. R21 / R24: order of checks on a linked receipt, as tested
Saving: unknown warehouse + unknown order -> `REFERENCE_NOT_FOUND` {`warehouseId`}; unknown order + unknown
article -> {`purchaseOrderId`}; closed order + unknown line -> `ORDER_NOT_OPEN`; another warehouse + wrong
article on line 0 + `orderLineNo` 99 on line 1 -> `REFERENCE_NOT_FOUND` {`lines[1].orderLineNo`} (kinds before
agreement); likewise unknown article, service article and a unit not on the article answer before
`ORDER_MISMATCH`.
Posting: one draft is refused five times in this order — `REFERENCE_INACTIVE` {`warehouseId`} ->
{`lines[1].articleId`} -> `QUANTITY_NOT_CONVERTIBLE` -> `ORDER_NOT_OPEN` -> `QUANTITY_EXCEEDS_ORDER` — then
posts as `SR-000001`.

### T-Q7. R20 on a document type that cannot carry the link
An `issue` / `transfer` / `count` with `purchaseOrderId` **and** `orderLineNo` on its lines: **tested** `400`
with (at least) the key `purchaseOrderId`; whether `lines[i].orderLineNo` is reported too is not asserted.

### T-Q8. Amount limits not tested
R9 limits a `lineAmount` to 9999999999.99; nothing limits `totalAmount` (200 such lines are about 2 × 10¹²).
The tests only use totals below the line maximum. Also untested: a product that is below the maximum before
rounding and above it after (`999999999.9995 × 10`). Should either be specified?

### T-Q9. R30: a posting racing with a close
Eight rounds of "post a draft receipt (1, 4)" against "close the order" in parallel. **Tested:** the close is
always `200`; the posting is `200` (then the closed order shows received 4) or `409 ORDER_NOT_OPEN` (then it
shows 0 and the receipt is still a draft). Both outcomes are accepted in every round.

### T-Q10. Things the criteria imply and the tests rely on
- AC-55 reads `reversalOf` from the items of `GET /stock-documents` (a list summary has it since spec 006).
- AC-65: `supplierId=abc` and `warehouseId=abc` -> `400` with that key (002/R19, as AC-54 says for
  `purchaseOrderId`); `search` does not match partner or warehouse names (R36 names `number` and `reference`).
- `purchase_order_get` with a malformed `id` -> tool error `NOT_FOUND` (as `partner_get`, `uom_get`).
- A reversing receipt writes its entries in line order (`-4`, `-5`).

## Answers from the architect to the tester (2026-10-09)

Every reading is confirmed. **No answer changes a test.** Two answers amend the spec (T-Q7, T-Q8); neither
contradicts a test.

### T-Q1
Confirmed; all of it is within AC-01. The count in the spec 008 test is part of "the literal tool list". The
new helper for pairs whose `quantity` is zero is right: `Stock.AssertStockEqualsLedgerAsync` stays as it is.

### T-Q2
Accepted. One set of abstract classes for both kinds of order is what the spec asks of the builder too (§11:
"a second user, not a copy").

### T-Q3
Confirmed as tested. By 001/R10 and §5 of spec 001 the key is the unknown property's name, so the builder
answers `purchaseOrderId`, `status`, `number`, `totalAmount`, `tenantId`; the tests need not pin it.

### T-Q4
Confirmed. The error codes come from 003 §5 ("the error codes it can return"), the other words from §5 of
this spec. Keep the assertions to "contains".

### T-Q5
Confirmed; that is R12 with 005/R13 as amended: header masters together and alone, then articles, then the
role, then conversion.

### T-Q6
Confirmed, saving and posting. For saving it is R21 in its order (warehouse reference, order exists, order
open, line kinds of 007/R16 with an unknown `orderLineNo` among `REFERENCE_NOT_FOUND`, then agreement); for
posting it is R24.

### T-Q7
Confirmed as tested. Decided, and R18 now says it: the type decides about `purchaseOrderId` only. A document
that sends a non-null `purchaseOrderId` is judged as linked by R20, so on an `issue`, a `transfer` or a
`count` with `purchaseOrderId` and a valid `orderLineNo` on every line the answer has the key
`purchaseOrderId` and no line key. Your "at least" assertion holds; you may tighten it, you need not.

### T-Q8
Both specified in R9, no test changes:
- `totalAmount` has no limit of its own. Its largest value is 200 × 9999999999.99, which the column holds.
- The maximum is compared with the **rounded** `lineAmount`. `999999999.9995 × 10` is 9999999999.995, rounds
  to 10000000000.00 and is refused with both keys; `999999999.999 × 10` is accepted, as you test.
A test of the refused case is welcome, not required; the builder covers it in AC-03.

### T-Q9
Confirmed; R30 allows exactly those two outcomes.

### T-Q10
All four confirmed: `reversalOf` is on the list summary (006 §4); malformed `supplierId` / `warehouseId`
filters are `400` with their key, and `search` matches `number` and `reference` only (R36); a malformed `id`
of `purchase_order_get` is `NOT_FOUND` (003/R15); a reversing document's entries follow the original's
(006/R14), so line order.

All rows confirmed against the rules named. None breaks a business rule.
