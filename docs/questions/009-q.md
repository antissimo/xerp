### B-D1. Disputed: seven tests reverse a receipt with a date earlier than the receipt's (006/R12)

before stock (order of checks of R12), so the answer is `400 VALIDATION_FAILED` with key `documentDate`

### B-D2. Disputed: one case of `AC26_Header_validation` expects a wrong JSON type together with invalid values
`PurchaseOrderDraftTests.AC26_Header_validation(case: "several fields at once")` sends
`{ "orderDate": "x", "supplierId": "abc", "warehouseId": 5 }` and expects the keys `orderDate`, `supplierId`
and `warehouseId` in one answer. `"warehouseId": 5` is a value of the wrong JSON type: by 001/E4 that is
refused when the body is bound, with the key of that property alone - before any value is validated - for
every operation since spec 001 (004/R15 says so in words: "of the wrong type, only that field is reported").
The answer is `400 VALIDATION_FAILED` with key `warehouseId` only. With `"warehouseId": "abc"` the three keys
come together, as R10 asks ("all fields and lines together"); a unit test of the builder covers that
(`OrderValidationTests.R3_…`). Suggested correction, the tester's: a string in place of `5`.

### B-Q1. The received quantity is a maintained column; which columns are progress and which are frozen
`PurchaseOrderLines.ReceivedBaseQuantity` is written only by `Order.Fulfil` (posting) and `Order.TakeBack`
(reversal), inside the posting and reversal transactions under the tenant's lock. Frozen at confirmation:
header and, per line, article, unit, quantity, unit price, factor, base quantity. Progress, not part of what
was ordered: `ReceivedBaseQuantity`. Lifecycle: `Status`, `ClosedAt`, `ClosedBy`. The DbContext guard (AC-02)
refuses every other change to a confirmed or closed order or its lines, tracked or not;
`PurchaseOrderImmutabilityTests` covers it. `receiptStatus` as a list filter is a plain predicate on that
column, and `incomingQuantity` a sum over it, joined with the ledger sums in one query (total and paging
count a pair once).

### B-Q2. Structure for spec 010
Domain: `Order<TLine>` / `OrderLine` hold everything common (lifecycle, lines, amounts, progress);
`PurchaseOrder` only names itself, and its table maps `PartnerId` / `DueDate` / `FulfilledBaseQuantity` to the
columns `SupplierId` / `ExpectedDate` / `ReceivedBaseQuantity`. `OrderAmounts` and `OrderProgress` are the
one amount function and the one progress function (AC-03, `OrderRulesTests`). Application: `OrderValidation`
and `OrderLinkChecks` take the kind (`OrderKind`: field names, role, series) and the link field as
parameters; `StockLineChecks.References` judges order lines like receipt lines. `PurchaseOrderOperations` is
written for purchase orders; when spec 010 arrives its body becomes the shared base and the purchase class a
thin subclass - I did not build the generic class for a single user.

### B-Q3. A stock document line repeats the document's order
§3 asks for a foreign key "from a linked stock document line to its order line". A line only has
`OrderLineNo`, so `StockDocumentLines` also carries `PurchaseOrderId` (null on an unlinked document, always
equal to its document's), and the key is (`TenantId`, `PurchaseOrderId`, `OrderLineNo`) ->
`PurchaseOrderLines` (`TenantId`, `OrderId`, `LineNo`). The column is not in any representation.
