# Spec 001 — questions from the builder

None of these blocked the implementation. Each states what was built, so the architect only has to confirm or
correct it.

## Q1. Unsupported method on a known path: 404 or 405?
`DELETE /api/v1/units-of-measure` (the path exists, the method does not). The error registry
(`docs/architecture.md` section 6) has no code for 405. **Built:** `404 NOT_FOUND` problem, the same as an unknown
path. Should there be a `405` with its own code instead?

**Answer (architect, 2026-10-09):** Confirmed: `404 NOT_FOUND`, the same problem as for an unknown path. There
is no `405` and no new code; for a client "this path with this method is not an operation" needs no different
reaction than "this path is not an operation". Recorded as spec 001 E11 and AC-72, and in the registry
(`docs/architecture.md` section 6). The existing test accepts `404` or `405`; tighten it to `404 NOT_FOUND`.

## Q2. Foreign keys on the audit columns
`UnitOfMeasure.CreatedBy` / `UpdatedBy` are "API key ids" (spec section 3). **Built:** real foreign keys
`(TenantId, CreatedBy)` and `(TenantId, UpdatedBy)` -> `ApiKeys (TenantId, Id)`, `ON DELETE RESTRICT`, following
architecture section 3 rule 4. Consequence: an API key that has written anything can be deactivated but never
hard-deleted. Is that the intended rule for the later key-management spec?

**Answer (architect, 2026-10-09):** Confirmed, and it is now the general rule (`docs/architecture.md` section 8):
every column that holds an actor is a foreign key `(TenantId, <column>)` -> `ApiKeys (TenantId, Id)` with
`ON DELETE RESTRICT`. The consequence you describe is intended and already decided in ADR-0010 (spec 003): API
keys are revoked, never deleted. Spec 002 (`Article.CreatedBy/UpdatedBy`) and spec 003
(`ApiKey.CreatedBy/RevokedBy`) now say the same.

## Q3. OpenAPI document
Spec 001 S1 says the OpenAPI document "may stay, in the Development environment only"; the amended architecture
section 7 calls it "the description they [CLI, web UI] build against". **Built:** no OpenAPI endpoint at all in
001 (the scaffold's was removed with `api/`; minimal-API endpoints that read the body strictly would also need
explicit request metadata to be described correctly). Which spec should deliver it, and should it be available
outside Development if external clients depend on it?

**Answer (architect, 2026-10-09):** Removing it in 001 was right; a document that describes strict bodies wrongly
is worse than none. It gets its own spec, **003a OpenAPI document** (`docs/roadmap.md`), after the MCP server:
a complete description of `/api/v1` including problem responses and error codes per operation, served in
**every** environment (external clients depend on it) at a route under `/api/v1` that requires a tenant API key
like every other route (so S1 keeps no exception), plus a generated copy committed to the repository with a
test that fails when the API and the committed copy differ. Spec 001 S1 no longer mentions a Development-only
document. Nothing to do on this branch.

## Q4. Admin key on an unknown path
Everything under `/api/v1` except `/api/v1/admin/*` is treated as a tenant route. **Built:** the admin key on
`/api/v1/nope` gets `403 FORBIDDEN` (not 404), and a tenant key on `/api/v1/admin/nope` gets `403` as well.
AC-71 only fixes the tenant-key case (404). Confirm.

**Answer (architect, 2026-10-09):** Confirmed for both. The kind of credential is checked before the existence
of the route: everything under `/api/v1/admin/` is an admin route, everything else under `/api/v1` is a tenant
route. This is also the safer design (a route added later cannot be left open by omission, and a wrong
credential learns nothing about which paths exist). Recorded as spec 001 S4 and AC-73; please add the test.

## Q5. Details the spec leaves open (built as follows)
- JSON property names in request bodies are case-sensitive: `"Code"` is an unknown property -> 400.
  Duplicate properties in one body are rejected too.
- `errors` key for a body-level failure (malformed JSON, empty body, array/null instead of an object) is `body`;
  for an unknown property or a wrong JSON type it is that property's name (e.g. `errors.foo`, `errors.name`).
- An empty query value (`?limit=`, `?isActive=`) is the same as an absent one. `isActive` accepts exactly `true`
  or `false` (lower case). A repeated parameter (`?limit=1&limit=2`) is a validation error.
- Unknown query parameters are ignored (so `?tenantId=…` has no effect rather than being an error).

**Answer (architect, 2026-10-09):**
- Case-sensitive property names and rejected duplicate properties: confirmed (spec 001 R14).
- `errors` key `body` for a body-level failure and the property's name for an unknown property or a wrong JSON
  type: confirmed and now part of the contract (spec 001 E4).
- Empty query value = absent; `isActive` exactly `true` / `false`; a repeated parameter is a validation error:
  confirmed (spec 001 R15).
- **Unknown query parameters ignored: not confirmed — they must be rejected.** `?serach=kg` returning the whole
  list is exactly the silent failure that R10 exists to prevent for bodies, and it is worse for an agent,
  which will act on the unfiltered result. Rule (spec 001 R15): a query parameter that the operation does not
  define, on any `/api/v1` route including those that define none, -> `400 VALIDATION_FAILED` with `errors`
  keyed by the parameter's name; parameter names are case-sensitive. `?tenantId=…` is therefore an error rather
  than a no-op, which still satisfies T1. This is required change 2 of `docs/reviews/001.md` (AC-59); the test
  `T1_No_query_parameter_or_header_selects_a_tenant` changes accordingly. Request headers other than
  `Authorization` stay ignored.
- Not asked, but found while reviewing and decided the same way: the `Content-Type` of a request is not
  examined (R14), and control characters in names and `search` are rejected (R4, R9; required change 1 of the
  review).

Specs 002 and 003 were updated to carry the same rules (002: R2, R3, R17a, AC-34, AC-73; 003: R1, R9a, AC-14).
