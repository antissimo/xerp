### T-Q2. Mirrored criteria
`SalesOrderTests.cs` runs the abstract classes of spec 009 (`009-q.md`, T-Q2) with the substitution table:
AC-10, 11, 20–28, 30–35, 63, 64 (009/AC-65), 49 (009/AC-48–50, 54), 80–82, 90–92, the mirrored part of 93, and
86–88 as far as they mirror. Where a mirrored test has to fulfil an order it first receives 1000 of A and B
into both warehouses (unlinked receipts), so that a delivery is never short there. Not mirrored 1:1:
- AC-34 "the independent series is `SI-`": the mirrored test posts an unlinked **receipt** between
  confirmations; `SalesOrderProgressTests.AC34_…` adds `SI-`, `PO-` and that a `PO-` number is not found
  under `/sales-orders/by-number` (and the reverse).
- 009/AC-64 (close whatever was received) has no number in this spec. Closing with nothing delivered is in
  the mirrored AC-63 tests; closing a partly delivered order in AC-60; closing a fully delivered sales order is
  not tested separately.
- 009/AC-72 (a reversal refused for stock) has no mirror: reversing a delivery only adds stock. **Tested
  instead** (R14): a delivery of the whole stock is reversed with `201`.

### T-Q3. AC-49 / E11 / R6: both links in one body
**Tested:** `400`, and `errors` has the key of the link that is on the wrong type — `purchaseOrderId` on an
`issue`, `salesOrderId` on a `receipt`. Also tested, as the mirror of the stated case: a sales order's id as
`purchaseOrderId` on a receipt -> `409 REFERENCE_NOT_FOUND` (`purchaseOrderId`); `"purchaseOrderId": null`
beside a `salesOrderId` (and the reverse) -> `201`, the other link `null` in the representation; either link
in a replace body -> `400`.

### T-Q4. R7: order of checks at posting, as tested
One draft delivery is refused six times in this order: `REFERENCE_INACTIVE` {`warehouseId`} ->
{`lines[1].articleId`} -> `QUANTITY_NOT_CONVERTIBLE` {`lines[0].quantity`} -> `ORDER_NOT_OPEN`
{`salesOrderId`} -> `QUANTITY_EXCEEDS_ORDER` {`lines[1].quantity`} -> (quantity corrected)
`INSUFFICIENT_STOCK` {`lines[0].quantity`, `lines[1].quantity`} -> (goods received) `200`, `SI-000001`.

### T-Q5. R9: stock is judged per article over the whole delivery
Order lines 1 and 3 are both 10 of A; 15 of A on hand; a delivery of 8 against each is within both order lines
and 16 in total. **Tested:** `INSUFFICIENT_STOCK` with keys `lines[0].quantity` and `lines[2].quantity` and
not the B line between them (005/R15: "all lines of each short article").

### T-Q6. AC-52: the race on stock, as tested
Ten rounds in one tenant: receive 10, two orders of 10, one draft delivery each, posted in parallel ->
exactly one `200` and one `409 INSUFFICIENT_STOCK` (`lines[0].quantity`), stock 0, one order `full`, one
`none`. The order that lost is closed before the next round so that every round starts with no reservation.
A second test races four deliveries and four unlinked issues of 3 for 10 on hand: exactly three `200`.

### T-Q7. Words asserted in tool descriptions (AC-85)
`stock_document_post` contains `INSUFFICIENT_STOCK`; `sales_order_get` contains `issue`, `salesOrderId`,
`orderLineNo`; `sales_order_create` contains `isCustomer`; `sales_order_confirm` contains
`availableQuantity`; `stock_on_hand_list` contains `incomingQuantity`, `reservedQuantity`,
`availableQuantity`. Nothing else is asserted about description text.

### T-Q8. Not specified, not asserted

counts, never the order.
