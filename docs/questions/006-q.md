## From the builder (implementation, branch `feat/006-stock-transfers-reversal`)

Nothing blocked the work and no tester test is disputed: all pass unchanged. Each point states what the code
does, so the architect only has to confirm or correct.

### B-Q1. Transfers and reversals take the per-tenant lock, not pair locks (§11, ADR-0013 last-but-one consequence)
As in spec 005 (005-q, B-Q2, still open): every stock-document write of a tenant - create, replace, delete,
post and now reverse - runs in one transaction that holds the tenant's row lock. So the builder note "lock the
pairs of both warehouses in one fixed order" is satisfied trivially: there is one lock, two postings can never
wait for each other (AC-39, E5), and a reversal racing a posting is serialised with it (AC-68, AC-69). The price
is unchanged: one tenant's stock writes run one after another. If 005 B-Q2 is answered with "finer locks",
transfers and reversals change with it in the same place (`StockDocumentOperations`).

### B-Q2. `REFERENCE_INACTIVE` on post reports every inactive master together (R5; replaces 005-q B-Q5)
Posting now reports the source (`warehouseId`), the destination (`toWarehouseId`) and every inactive article
(`lines[i].articleId`) in one error, as T-Q3 reads 005/R13. In spec 005 I had reported an inactive warehouse
alone (005-q, B-Q5); that is withdrawn. No spec 005 test had to change.

### B-Q3. `PUT`: where the destination rule sits in the order of checks
Whether `toWarehouseId` is required or forbidden depends on the type, and a replace has no `type` - only the
stored document knows. So on `PUT` the order is: form of all fields (`400`) -> `404` -> destination rule
(`400`, key `toWarehouseId`) -> `INVALID_STATE` -> references. Consequences: `PUT` on an unknown id with a
body that lacks `toWarehouseId` is `404`, not `400`; `PUT` on a posted transfer without `toWarehouseId` is
`400`, not `INVALID_STATE`. On create the rule is part of the form, with the other invalid fields.

### B-Q4. Order of the two entries of a reversing transfer line
R14 gives none and the tests assert none (T-Q6). The ledger orders by posting time, number, line and then
quantity, so within a line the negative entry always comes first: for a transfer the source (R6), for its
reversal the destination.

### B-Q5. Reverse without a body, and the unknown property
`POST /{id}/reverse` without any body is read as `{}` and answered `400` with key `documentDate` (AC-64); every
other endpoint still answers a missing body with key `body`. An unknown property is reported under its own
name, so `"lines"` gives key `lines` (T-Q5).

### B-Q6. `INSUFFICIENT_STOCK` on a reversal: which lines
A pair (article, warehouse) is short when stock on hand plus the reversing entries of that pair is below zero;
the keys are `lines[i].quantity` of every line of the original that names a short article (R16, as 005/R15).

### B-Q7. The DbContext rule for S2 is stricter than the text
A posted document may be saved changed only when exactly `Status` (`posted -> reversed`) and `ReversedById`
(null -> id) changed **and** the document it names is inserted by the same save as a posted document whose
`ReversalOfId` is the original. Marking a document reversed without its reversing document is refused.
The database additionally allows one reversing document per original (unique `(TenantId, ReversalOfId)`).

### B-Q8. Earlier tests changed
Only my own unit tests of spec 005: the invalid `type` value `"transfer"` became `"return"` (as AC-01 allows
for the tester's), the tool count is 33, and calls follow the new signatures (`toWarehouseId`). No assertion
was weakened; no tester test was touched.
