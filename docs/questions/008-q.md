### T-Q3. R9: order of checks on posting, as tested
One draft count that is at once outdated, not convertible and has an inactive article is posted three times:
`REFERENCE_INACTIVE` -> (article reactivated) `QUANTITY_NOT_CONVERTIBLE` -> (factor restored) `COUNT_OUTDATED`.

### T-Q4. R10: an outdated count whose counted quantity equals the stock of now
Book 100, counted 97, then an issue of 3. Posting would write no entry and stock already equals the count,
but stock (97) differs from the book quantity (100). **Tested:** `COUNT_OUTDATED`; after a save the line shows
difference 0 and the count posts without entries. Is that right, or should it post?

### T-Q5. Reversal and the book quantity
- A reversal is never judged "outdated": a count of 97 (book 100), then an issue of 50, then the reversal ->
  `201`, stock 50.
- The reversing document's `lines` are compared with the original's as whole JSON values (R17: copies,
  including `bookQuantity` and `differenceQuantity`), so its `differenceQuantity` has the original's sign
  while its entry has the opposite one (AC-60).

### B-Q1. Replace with a quantity of `0` when no document has that id
The body of a replace has no `type`, so whether `0` is acceptable (R4) is known only from the stored document
— like the destination rule (006/R4: form -> `404` -> destination rule -> `INVALID_STATE` -> references).
But the spec 005 test `StockDocumentDraftTests.AC74_R8_Validation_precedes_the_existence_check_on_replace`
sends quantity `0` to a random id and expects `400` with key `lines[0].quantity`. **Built:** a `0` addressed
to no document is `400` (`0` is valid on a count only, and there is no count there); a repeated article or a
`toWarehouseId` addressed to no document is `404`, as 006/R4 says. With a stored document the order is:
form -> `404` -> rules of the type (`toWarehouseId`; `0` on a document that is not a count; a repeated article
on a count — all together, `400`) -> `INVALID_STATE` -> references. Confirm, or say that `0` on an unknown id
should be `404` (then AC-74 of spec 005 has to change).

### B-Q2. Create with an unknown `type`
The lines are then judged like those of a receipt: `0` is invalid, repeats are allowed. `{ "type": "return",
… quantity 0 }` gives keys `type` and `lines[0].quantity`.

### B-Q3. Smaller readings
- A draft count line that no longer converts (007/R17, T-Q7) shows the `baseQuantity` R14 gives and
  `differenceQuantity` = that − `bookQuantity`; only saving and posting refuse it.
- `BookQuantity` is `NULL` on lines of the other types and is written by create and replace only; the
  difference is not stored — it is `BaseQuantity − BookQuantity` (posted) or computed when a draft is read.
- `StockDocument.Reverse`: the guard is relaxed for counts only, and made exact there — a count is reversed
  with as many entries as it has lines with a difference (none for a count without differences); the other
  types still need at least one entry.
- Order on posting a count (R9): … masters active -> conversion -> current (`COUNT_OUTDATED`) -> number.
  The stock compared is read under the per-tenant lock, in the posting transaction (ADR-0012, amendment).
- Create and replace of a count read the book quantity under the same lock, so a count cannot be saved
  against stock that a concurrent posting is changing.
- The migration `StockCount` adds one nullable column, `StockDocumentLines.BookQuantity`; no data is touched.
