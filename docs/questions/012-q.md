# Spec 012 — questions

## From the tester (acceptance tests, branch `tests/012-configurable-rules`)

Written against the rewritten spec (boolean switches, commit `0249eb6`); nothing of the first text is left in
the tests. None of these blocked the tests. Each states what the tests do, so the architect only has to
confirm or correct.

### T-Q1. Changes to earlier tests (AC-01)
Made on this branch only, all in `McpToolListTests`:
- Item 1 — the literal list (`Spec012Tools`, 62 names) and the three places that repeat the count (the
  list test, the spec 008 test, the spec 011a `partnerId` test).
- Item 4 — the pinned `required` of `purchase_order_create` and `sales_order_create` loses `supplierId` /
  `customerId`. Nullability of the argument and of `supplier` / `customer` in the output schemas is asserted
  by new tests (`S012_…`), not by changing old ones.
- Items 2 and 3 — **nothing had to change.** No earlier acceptance test pins the exact member set of a
  problem document or tool error, and none pins the error-code list of a description (they use "contains").
  The rows "partner missing" and "partner null" of 009/AC-26 (`OrderDraftTests`) assert `400` with the key
  and stay as they are; that the refusal now names the rule is asserted by 012/AC-80.
- Item 5 is the builder's (`Xerp.UnitTests`: the tool count 57 in `McpToolTests`, the constraint test).
No test that asserts a status, a code, an `errors` key, a quantity, a number or a state changed.

### T-Q2. "refused by": the order of `fields`
Section 4 says `fields` are the `errors` keys the rule produced "in the order they appear in `errors`".
**Tested:** `rules[0].fields` is sequence-equal to the keys of `errors` in the order of the JSON document
(for a mixed `400`, E12: exactly `["supplierId"]`). Each element of `rules` has exactly `key`, `value`,
`fields`, and `value` is a JSON boolean.

### T-Q3. AC-97: two parallel Sets always leave two changes
With R7 (a Set of the default's own value is a change) both orders record two changes. **Tested:** the older
change is `default -> not final`, the newest `not final -> final`, the newest's `changedAt` and `changedBy`
are the rule's `updatedAt` / `updatedBy`. Run for a rule whose default is `false` and one whose default is
`true`, five rounds each, the two Sets sent with two different keys.

### T-Q4. R8: a changeless Set by another key
**Tested:** the second Set of the same value, sent by a *different* key, answers the rule exactly as the
first left it — `updatedAt` and `updatedBy` are still the first key's — and records no change.

### T-Q5. R9 with R7: reset of a tenant value that equals the default
Set(`sales.partnerRequired`, `true`) then reset. **Tested:** the reset "changes something" (it removes the
tenant's value), so it records a change `{ action: "reset", oldValue: true, newValue: true }` and the rule is
back at `source == "default"` with the reset's `updatedAt`. If such a reset should record nothing, the test
`AC35_R9_Reset_removes_a_tenant_value_that_equals_the_default` has to change.

### T-Q6. R32: values of `supplierId` / `customerId` that are neither a uuid nor null
The spec names `"abc"`. **Tested** as the same invariant (`400`, key `supplierId`, no `rules`, whatever the
rule's value): `"abc"`, `""` and the number `5`.

### T-Q7. R36 on replace
011a/R8–R9 speak of create and replace. **Tested:** replacing a linked draft of an order without a partner
with a non-null `partnerId` is `409 ORDER_MISMATCH` with key `partnerId`; with `null` it keeps
`partner == null`.

### T-Q8. Tool schemas (section 5)
**Tested:** `rule_set.value` allows **only** `boolean` (no `null`, no string); `rule_set` requires `key` and
`value`; `supplierId` / `customerId` allows string and null on create and update, is in `required` only on
update; the output schema of `…_get`, `_create`, `_update`, `_confirm`, `_close`, `_reopen` allows `null` for
`supplier` / `customer`. The summary inside `…_list`'s output schema is not asserted (no fixed place to find
it). The input schema of the four order tools is JSON-equal before and after a `rule_set` (AC-114).

### T-Q9. Tool descriptions (section 5)
No sentence is pinned. **Tested** as substrings: `STOCK_RESERVED`, `stock.negativeStockAllowed`,
`sales.reservedStockProtected` and the word `rules` in `stock_document_post` and `stock_document_reverse`;
the two over-fulfilment keys in `stock_document_post`; `purchase.partnerRequired` / `sales.partnerRequired`
in the four order tools; "default" and "description" in `rule_list`, "default" in `rule_reset`, "existing"
and "key" in `rule_set`.

### T-Q10. AC-113: `detail` of a refused posting
**Tested:** for the same draft, `code`, `detail`, `errors` and `rules` of the HTTP problem and of the tool
error are JSON-equal (003/AC-04: a tool error has the same detail). For the Set and the reset two tenants in
the same state are compared, `updatedAt` / `updatedBy` (changes: `id`, `changedAt`, `changedBy`) aside.

### T-Q11. E3: other methods on the rule routes
Beyond `DELETE /rules/{key}` and `POST /rules`, **tested** as `404` (001/E11, S2): `POST /rules/{key}`,
`GET /rules/{key}/reset`, `DELETE /rule-changes`, `POST /rule-changes`.

### T-Q12. AC-96: how many of the ten issues post
The spec fixes the invariants, not the count. **Tested additionally:** at least five are posted (stock is 5,
so five fit whatever the order), every refusal is "refused by" (`INSUFFICIENT_STOCK`,
`stock.negativeStockAllowed`, `false`), and the Set itself answers `200`.

### T-Q13. R27 beyond the criteria
Two cases that follow from R27 / R28 and have no criterion of their own are tested, so a builder who reads
R27 differently sees it at once:
- over-delivery allowed, stock 20, SO1 [A, 10] and SO2 [A, 10] (available 0): Deliver 11 for SO1 ->
  `STOCK_RESERVED` (stock 9, still reserved 10); Deliver 10 -> posted;
- over-delivery allowed, stock 20, one SO [A, 10]: Deliver 15 -> posted (nothing is reserved afterwards, so
  the first condition of R27 does not hold).

### Not covered by acceptance tests
- AC-01 (manual), AC-02 to AC-06 (builder, manual).
- S3 (what logs record) and S4 (a stored row with an unknown key): not reachable through the public surface.
- R39, "one element per rule that contributed": no request of this spec can be refused by two rules at once

  element wherever it appears.
- R14 beyond AC-96 and AC-97 (the lock itself is the builder's).
