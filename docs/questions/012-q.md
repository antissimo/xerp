## From the builder (implementation, branch `feat/012-configurable-rules`)

### B-Q1. DISPUTED — six acceptance tests reverse a linked document with a date before the document's own (not changed by the builder; they fail)
One cause, six tests (four methods, two of them run for purchase and for sales):
- `RuleOverFulfilmentTests.AC62_Switching_back_changes_nothing_received_and_refuses_the_next_receipt`
- `RuleReservedStockTests.AC73_R28_Reversing_an_issue_or_a_delivery_is_never_refused_by_this_rule`
- `PurchasePartnerRequiredTests` / `SalesPartnerRequiredTests` `.AC84_AC87_With_the_rule_off_an_order_without_a_partner_is_confirmed_fulfilled_closed_and_reopened`
- `PurchasePartnerRequiredTests` / `SalesPartnerRequiredTests` `.AC89_Back_on_the_rule_judges_the_next_save_and_not_the_life_of_an_order_without_a_partner`

Each reverses a **linked** receipt or delivery with `Stock.ReverseAsync(http, id)`, whose date defaults to
`Stock.Date` (`2026-10-09`). A linked document is created by `OrderApi.Document` with `documentDate =
Stock.NextDay` (`2026-10-10`, `OrderSupport.cs`). The reversal is therefore dated one day **before** the
document it reverses, and the answer is `400 VALIDATION_FAILED`, key `documentDate` — 006/R12, an invariant
that spec 012 does not touch (R40: codes, statuses and keys of specs 001–011a are unchanged) and that
`StockReversalTests` pins. The tests expect `201`.

Everything these tests assert **before** that line passes. Checked without committing anything: with the
default date of `Stock.ReverseAsync` set to `Stock.NextDay` locally, all six pass in full; the tester's file
was restored afterwards and is unchanged on this branch. Proposed correction, for the tester: pass
`Stock.NextDay` in the five call sites (`RuleOverFulfilmentTests` l. 136, `RuleReservedStockTests` l. 154,
`RulePartnerRequiredTests` l. 196 and l. 319). The implementation was not bent to make them pass: accepting
a reversal dated before its original would break 006/R12 and its tests.

### B-Q2. Earlier builder tests changed (AC-01, item 5) — and why more than the two the spec names
- `StockBalanceBuilderTests.AC02_…_and_a_negative_balance`: the two statements that expected the check
  constraint are removed and the test renamed; `RuleBuilderTests` asserts that `StockBalances` has no check
  constraint and that the stored balance follows the ledger below zero (and that rebuild restores a negative sum).
- `StockBalanceRulesTests`: "a balance never goes negative" became "a balance follows the ledger below
  zero"; `CorrectTo(-1)` no longer throws.
- `StockCountRulesTests`: a negative book quantity is now accepted (R20, AC-53).
- `McpToolTests`: 57 -> 62.
- **Signatures, not behaviour**: the six checks take the rule's boolean as a required argument (AC-04), so
  every earlier unit test that called them now passes `false` / `true` — the default — explicitly
  (`OrderRulesTests`, `SalesOrderRulesTests`, `OrderValidationTests`, `DefaultWarehouseRulesTests`,
  `StockDocumentRulesTests`, `StockDocumentValidationTests`, `StockUnitLineRulesTests`,
  `StockTransferReversal*Tests`, `StockCountRulesTests`). No expected value in them changed. There is no
  default parameter value anywhere: a caller cannot forget the rule.
- `StructureTests`: `RuleValues`, `RuleChanges` added to the named tables.

### B-Q3. R9: where `updatedAt` / `updatedBy` come from after a reset
Reset removes the `RuleValue` row (section 3), so the row cannot carry "those of the reset". **Built:** a rule
without a row shows `changedAt` / `changedBy` of its newest `RuleChange` (the reset), and `null` when it has
no change. With a row, the row's own `UpdatedAt` / `UpdatedBy` — which by R8 always equal the newest change.

### B-Q4. R5 with a tool: `key` and `value` both missing
`rule_set {}` answers `VALIDATION_FAILED` with both keys, `key` and `value` (both are the form of the
request). `key` given as `""` is a string that is no rule: `NOT_FOUND`, as over HTTP (R4).

### B-Q5. R27: when the reserved quantity is read
The pair's reserved quantity is read inside the posting / reversal transaction, under the tenant's lock, and
**only when `sales.reservedStockProtected` is `true`** and the operation lowers a pair: with `false` it decides
nothing (R26), so a tenant at the default pays no extra query. The boolean still goes to the Domain function
(`StockMovements.TakesReserved`), which is what refuses. "After" for a delivery is the reserved quantity minus
`min(document quantity, outstanding)` per order line it names (R28).

### B-Q6. R17: one comparison
`StockMovements.GoesBelowZero(onHand, delta, negativeStockAllowed)` is the only place the comparison is
made; issue, transfer source, delivery and every reversal go through `StockMovements.ShortPairs`.
`StockSufficiency.ShortLines` and `StockMovements.ShortArticles` are gone. Stock is read for a posting only
when it lowers a pair (a receipt reads none), as before.

### B-Q7. R22 expressed through the outstanding quantity
`OrderProgress.Exceeds(ordered, fulfilled, document, allowed)` is R22 literally. Posting asks it per order
line through `ExceedingLines`, which is given what each line has outstanding — `max(0, ordered − fulfilled)`
(R23) — i.e. `Exceeds(outstanding, 0, document, allowed)`. The two agree for every document quantity above
zero, also for a line already above its ordered quantity (outstanding 0: any further quantity exceeds, R24).

### B-Q8. Smaller choices, for confirmation
- The rule read for create / replace of an order happens before the lock, with the validation of the body
  (section 11 allows it); the rule is not read again in that operation. Confirm, close and reopen read no rule.
- `GET /rules` and `GET /rules/{key}` take no lock and read values and history in two queries without a
  snapshot; a change committed between them can show a rule whose `updatedAt` is one change older than its
  `value` for that one response. Say if the reads should use one snapshot (`AtOneMomentAsync`).
- `search` of `GET /rules` matches `key` or `name`, case-insensitive (the registry is in memory).
- The history of rule changes is refused for update and delete in `SaveChanges`, like the stock ledger.
- Descriptions of the rules (`description`) and the new sentences in the tool descriptions are the builder's
  wording; none is pinned by a test beyond the substrings of T-Q9.
- The MCP server instructions mention `rules?` in the error shape.
