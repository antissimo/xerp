**Set, reset, history (R7–R11).** Set and reset run inside `SerializedPerTenantAsync`, read the stored row
under the lock, and write the value and its `RuleChange` in one `SaveChanges` with one `now` and the acting
key; a Set of the stored value and a reset without a row write nothing (R8, R9). `oldValue` / `newValue` are

The history is refused for update and delete in `SaveChanges`, as the ledger is. Both tables are

keys `(TenantId, …)` -> `ApiKeys` with `RESTRICT`. No `IgnoreQueryFilters()` in the diff. AC-30–AC-37,
AC-97, AC-100, AC-101 and the builder's AC-02 tests pass.

**New writes only (R13–R16).** A change touches `RuleValues` and `RuleChanges` and nothing else. Confirm,
close and reopen read no rule; posting and reversal read only the stock and order-quantity rules; reads
apply none. AC-54, AC-62 (up to line 136), AC-91 and AC-95 pass.

**Errors name the rule (R38, R39).** `AppError.RefusedBy(rule, value, fields)` is the one place a refusal is
attached; `Problems.ToBody` and `ToolResults.Error` each serialise `rules` once and omit it when null.
`INSUFFICIENT_STOCK`, `QUANTITY_EXCEEDS_ORDER` and `STOCK_RESERVED` carry every key of `errors`; a mixed
`400` carries the partner key alone (`OrderValidation.Values`), and a malformed or absent-on-replace
partner is an invariant's refusal without `rules` (R32). AC-42–AC-44, AC-112, AC-113 pass.

**Negative stock: the balance, the ledger and the lock (R17–R21).** The stored balance is still written
only where ledger entries are (`StockBalances.AddAsync` in `PostAsync` and `ReverseAsync`) and by rebuild,
all three under the tenant's lock, so stored == sum of the ledger for either value (AC-50–AC-53; builder's
`R19_…`). With the database check gone, what keeps a tenant with the rule off from going below zero is the
check under the lock, and there is no window in it:
- `PostAsync` and `ReverseAsync` call `rules.ReadAsync` as the first statement after
  `SELECT … FOR NO KEY UPDATE` on the tenant; the transaction is `READ COMMITTED`, so that read sees every
  change committed before the lock was granted — and a Set commits before it releases the lock;
- stock on hand of the lowered pairs is read after that, in the same transaction, and the balance is saved
  before the lock is released; parallel postings queue on the same row lock;
- Set and reset take the same lock, so a posting is judged entirely before or entirely after a change.
A count is not judged (R29) and cannot lower a pair below zero: its "current" check runs under the lock and
it brings the pair to the counted quantity. AC-95 (20 rounds), AC-96 (10 parallel issues against a Set) and
the races of spec 011 pass.

**`sales.reservedStockProtected` refuses exactly R27.** `TakesReserved` is the three conditions literally:
`delta < 0`, reserved after above zero, `A_after < 0` and `A_after < A_before`. Reserved-before is read
under the lock (only when the rule is `true`, B-Q5); reserved-after subtracts, for a delivery, `min(document
quantity, outstanding)` per order line (`OrderProgress.Released`), so a delivery within its order leaves
availability unchanged and the part above it is judged. A reversal releases nothing; reversing an issue or
a delivery lowers no pair and is never asked. Order of stages: order quantities -> stock -> reservation,
each answering alone; the two stock rules are independent. AC-70–AC-72, AC-74–AC-78, AC-73 up to line 154,
T-Q13 pass.

## Non-blocking

1. **`GET /rules` reads values and history in two statements without a snapshot** (B-Q8). A response that
   overlaps a change of a rule can show the old value with the new change's `updatedAt`, once. Set and reset
   answer from inside the lock and are exact. `AtOneMomentAsync` would close it if it ever matters.
2. **Two changes of one rule in the same microsecond** are ordered by `Id` (uuid v7: milliseconds, then
   random), in the history and for "the newest change" after a reset. It needs two Sets under the lock
   within one timestamp of the database; then the order shown may be the reverse of the order applied.
3. **The posting reads all of the tenant's rule values and, when reservation is protected, the outstanding
   sales lines of the lowered articles and warehouses, inside the lock.** A handful of rows today; it grows
   with the registry (013, 014) and with open orders. Measure before caching (ADR-0020, decision 10).
4. `RuleChanges` is keyed by `Id` alone, like the ledger; the tenant is in its foreign keys and filter.
   Consistent with the other append-only table.
