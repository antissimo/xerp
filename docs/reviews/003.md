## What was checked

Tenant scoping
- Every key-management query goes through `IXerpDb.ApiKeys`, which carries the tenant filter; list, get and
  revoke therefore cannot see another tenant's key, and revoke returns `NOT_FOUND` for one (T4).
- A created key takes `TenantId` and `createdBy` from the request's tenant context, never from input; the
  input type has only `name` and `actorType`, and unknown properties are rejected (R3, R4).
- `/mcp` is guarded by the same middleware as `/api/v1`, by path, before any JSON-RPC handling. Tenant and
  actor are set once per HTTP request; the server is stateless, so nothing survives the request (T1, T2).
- No tool has a tenant argument; all 14 input schemas are closed and binding rejects unknown arguments.
- `IgnoreQueryFilters()` still occurs once in `src`, in the authentication lookup (T5).
- The tool list, schemas and `instructions` are static fields built at start-up (T6).

Thin MCP layer (R12, AC-03)
- `Xerp.Api.Mcp` references no EF type, no `IXerpDb` and no DbContext.
- Each tool binds, calls one Application operation and maps the result through one mapper (`ToolResults`).
  Tool arguments are bound by the same strict JSON binder as HTTP bodies, so the `errors` keys agree.
- "Exactly one of `id`, `code`" and "an id that is not a UUID names no record" are in
  `Xerp.Application.Common.RecordAddress`, tested without MCP or HTTP.

Secrets (S3)
- The plaintext exists only in `CreatedApiKeyDto`, returned only by `ApiKeyOperations.CreateAsync`, called
  only by `POST /api-keys`. No tool reaches it; `ApiKeyDto` has no key and no hash.
- The `201` response sets `Cache-Control: no-store`. The only new log line records the tool name and the
  exception of an unexpected failure.

Revocation (R5–R8)
- Self-revocation is refused before anything else. Revocations of a tenant run under a row lock on the
  tenant, and the acting key is re-read after the lock is obtained; the loser of a mutual revocation gets
  `UNAUTHENTICATED`. This is the database-level guarantee §11 asked for.
- `ApiKey.Revoke` is a no-op on an inactive key, so the first `revokedAt` / `revokedBy` are kept.

Data (AC-02)
- One migration added (`ApiKeyLifecycle`): three nullable columns, two indexes, two composite foreign keys
  `(TenantId, CreatedBy|RevokedBy)` -> `ApiKeys (TenantId, Id)`, `RESTRICT`. Earlier migrations are untouched.

Review 001, non-blocking item 1 — **done.** `Tenants` is removed from `IXerpDb`; `WhoAmI` reads the current
tenant through the port `ICurrentTenantReader`, whose implementation reads only the tenant of the request.
No Application or Api code can query the tenant table any more.

Builder's questions B-Q1 … B-Q7 were answered on `main` (`docs/questions/003-q.md`); the implementation
matches the answers. When merging, the file conflicts: keep the version on `main`.

## Non-blocking

1. The description of `api_key_revoke` does not mention `UNAUTHENTICATED` (5.3 as amended after B-Q2). An
   agent that loses the race gets a code its tool description never named. Add one sentence.
2. The descriptions of the tools with a required `id` (`*_delete`, `api_key_get`, `api_key_revoke`) do not
   mention `VALIDATION_FAILED`, which they return for a missing or non-string `id` (R15).
3. `ToolArguments.BindWithId` decides "`id` must be a string" in the Api layer. It is a JSON-type check, the
   same kind the body binder makes, so R12 holds; but its message is the one piece of validation text that
   lives outside Application. Fine as is; do not let it grow.
4. A tool receives `IServiceProvider` and resolves its operation from it. AC-03 holds by the letter, yet
   nothing stops a later tool from resolving `IXerpDb`. The tester's reflection test would not catch that.
   Consider a typed delegate per operation class when the catalogue is next touched.
5. Binding errors for tool arguments reuse the HTTP wording ("The request body must be a JSON object …").
   Only `detail` is affected; `code` and `errors` keys are right.
6. `ApiV1Middleware` now guards `/mcp` as well; the name no longer says so (B-Q5). Rename when convenient.
7. The manual check of §11 was made with `curl`, not with a real agent client (B-Q7). Accepted; the official
   C# client is exercised by the tester's suite. Worth doing once by the owner before the first outside user.
8. Review 001 item 3 is also done here (an `UNAUTHENTICATED` returned by an operation now carries
   `WWW-Authenticate: Bearer`, B-Q6). Items 4–7 remain open and non-blocking.
