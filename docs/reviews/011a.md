**Tenant scope.** `PartnerId` sits on a tenant-owned row and its foreign key includes `TenantId` (T1).
Every read of a partner — reference check, role, representation, `IN_USE`, list filter — goes through the
filtered `IXerpDb`; the diff adds no `IgnoreQueryFilters()`. Another tenant's partner is "not found" on an
unlinked document and an ordinary mismatch on a linked one, because there it is only compared (T2). The
migration joins each document to an order of its own tenant. AC-70, AC-71 and the builder's T1 test pass.

**Layers.** Domain: which types can name a partner, and the copy on reversal. Application: everything else
(`StockPartnerChecks`, `PartnerChecks`, `OrderLinkChecks`, `StockDocumentOperations`). `Api`: one query
parameter bound in `StockEndpoints`; schemas and descriptions in `ToolCatalog`. No rule there (AC-03).

**Security (§9).** The diff adds no logging. Error bodies carry the key `partnerId` and, at most, the id the
caller sent; `ORDER_MISMATCH` does not reveal the order's partner. No code or name of a partner is in any
message.

   tenant lock (partner writes do not take it). The same holds for articles since spec 005 and for the
   partner of an order since 009; the next posting check or the foreign key catches what matters. Not new,
   not added to `open-items.md`.
