## AC-85 (create article racing with delete of its unit) — no race found

The builder saw this test fail once in an intermediate run and pass later, without investigating. Decision:
neither the test nor the implementation has a race; it is **not** a required change. Grounds:

1. *The implementation, by analysis.* Both sides end in a single statement whose outcome the database decides,
   and both possible errors are translated:
   - `POST /articles`: pre-check of the unit, then `INSERT`. The foreign-key check of the insert takes a
     key-share lock on the unit row. If the unit's delete committed first (or commits while the insert waits
     for it), the insert fails with `23503` on `FK_Articles_UnitsOfMeasure_TenantId_BaseUnitId`, which
     `XerpDbContext.Translate` turns into `ForeignKeyViolationException(BlockedDelete: false)` and
     `ArticleOperations.SaveAndReadAsync` into `409 REFERENCE_NOT_FOUND`.
   - `DELETE /units-of-measure/{id}`: count of referrers, then `DELETE`. If the article's insert committed
     first (or commits while the delete waits for its key-share lock), the delete fails with `23001`
     (`RESTRICT`, PostgreSQL 18) — or `23503`, also handled — translated to `BlockedDelete: true` and to
     `409 IN_USE`.
   - The delete never waits for an uncommitted insert it cannot see while that insert waits for the delete, so
     there is no deadlock; whichever statement takes the unit row first wins, and the other gets the matching
     `409`. The four combinations the spec forbids — (`201`, `204`), (`409`, `409`), any `500`, a dangling
     reference — cannot be produced.
   - The read of the unit's code and name after a successful save cannot fail: the committed article holds
     the unit.
2. *The test, by inspection.* It asserts exactly the two allowed pairs, then that the unit exists exactly when
   the article was created, and finally that every article points at an existing unit. It depends on no
   timing, no ordering between the two requests and no shared state: one tenant per run, fresh unit and
   article codes per round.
3. *By repetition.* The test was run 41 times in isolation (820 rounds) and 4 times inside the full
   integration suite on `2bb6fa9`: 0 failures.
4. *History.* The test and the three files involved (`ArticleOperations`, `UnitOfMeasureOperations`,
   `XerpDbContext`) have not changed since `85f02ee`; what changed afterwards is input validation only.
   The deterministic halves are also pinned separately, by the tests
   `AC85_DbContext_translates_a_delete_blocked_by_the_foreign_key` and
   `T5_DbContext_cannot_store_an_article_pointing_at_another_tenants_unit`.

What remains is that an unexplained red run was not recorded. See non-blocking 1 and the note for the
orchestrator: the next failure must be diagnosable from its output alone.

## What was checked and found correct

Business rules
- Order of checks (R13, ADR-0008 decision 7): validation -> addressed article -> base unit
  (`REFERENCE_NOT_FOUND`, then `REFERENCE_INACTIVE`) -> code. Validation reports all fields at once and does
  no lookup of the unit (AC-43, AC-44, AC-57).
- Base unit (R5–R9): required for both types; an inactive unit is refused only when newly assigned — a replace
  that keeps the current unit succeeds after the unit was deactivated (AC-56); the representation shows the
  unit's current code and name by a join at read time, and changing the unit does not touch the article's
  `updatedAt` / `updatedBy` (AC-45).
- `IN_USE` (R16, R17): active and inactive referrers both block the delete; the count is taken through the
  tenant-filtered context; deactivating and renaming a referenced unit stay allowed; the unit can be deleted
  once the last article is deleted or moved (AC-80…AC-84).
- Replace (R11, R12): all six fields must be present; an omitted `description` is distinguished from
  `"description": null` (AC-51, AC-52); own code and case-only change never conflict.
- Description (R3) and name (R2): trimmed, empty -> `null`, 2000 characters, LF/CR/tab kept, every other
  control character rejected; names reject all control characters (AC-34). The rules are in Domain
  (`ArticleRules`, `NameRules`, `TextRules`).
- `type` is exact and case-sensitive on write and as a filter; article and unit codes are separate namespaces
  (AC-33).
- List (R18, R19): shared `ListRules` for search and paging; `type` and `baseUnitId` filters; an unknown
  `baseUnitId` gives an empty result; description is not searched; unknown query parameters rejected on every
  article route (AC-73).

Data and tenant isolation
- Exactly one migration added (`20261008220859_Articles`); spec 001's migration files are not in the diff.
- Foreign keys: `(TenantId, BaseUnitId)` -> `UnitsOfMeasure (TenantId, Id)`, and both audit keys ->
  `ApiKeys (TenantId, Id)`, all `RESTRICT`; unique `(TenantId, lower(Code))`; the foreign-key index serves
  "articles by base unit".
- The AC-04 model test enumerates every foreign key between tenant-owned entities, requires `TenantId` in the
  same position on both sides, and additionally requires that no foreign key in the model cascades or nulls.
  AC-05 / AC-06 check the database itself with raw SQL and assert the constraint name.
- `Article` is `ITenantOwned`; no `IgnoreQueryFilters()` was added (the key lookup of spec 001 is still the
  only one). Another tenant's unit as `baseUnitId` gives a body identical to a random id's (AC-95).

Layering and security
- Endpoints bind, call one operation, map the result. The reference check (`ReferenceCheck`), `IN_USE` and
  the order of checks are in Application; Npgsql stays in Infrastructure (`Translate`). Application sees
  `ForeignKeyViolationException` with "blocked delete or missing target", as ADR-0008 decision 6 asks.
- Error bodies carry no constraint names or SQL; the test helper now also fails on `FK_…`, `IX_…` and
  `violates foreign key` in any problem body.
- Spec 001 tests: two were edited and none weakened (`002-q.md`, Q1, approved): the table-list test expects
  `Articles`, and the unknown-path example moved off `/api/v1/articles`.
- No skipped tests, no conditional compilation.

## Non-blocking

1. **Make AC-85 diagnosable.** On a failure the test reports one assertion without the round or the other
   request's result. Assert with a message that carries the round number and both statuses and bodies. The
   test also passes if all 20 rounds end the same way; counting the two outcomes in the test output would
   show whether the race path is exercised at all (do not assert on the split — it depends on timing).
2. The unknown-path example in `ErrorModelTests` is now `/api/v1/partners`, which spec 004 claims. Change it to
   `/api/v1/no-such-resource` (`002-q.md`, answer Q1) no later than the first commit of spec 004.
3. `DbNames` in Application grew by one index name and one foreign-key name (review 001, non-blocking 5).
   Spec 004 adds two masters and spec 005 several references; before that list grows further, let
   Infrastructure report a violation by meaning (which entity, which field) rather than by constraint name.
4. `UnitOfMeasureOperations.DeleteAsync` counts all referencing articles to print the number. Spec 005 adds
   more kinds of referrer; an existence check per kind is enough, and the number may be dropped (the spec
   only allows it, S3).
5. `ArticleOperations.ListAsync` orders twice (inside the page and again after the join). Correct, and needed
   because a join does not preserve order; a one-line comment would stop someone from "simplifying" it.
6. A successful create or replace answers from two statements (save, then read of the unit). Accepted in
   `002-q.md` Q5; when documents with many references arrive (005), build the response from one read.
