**Per-tenant lock on every stock-relevant write (open item 005/2) — done for 010.** Sales orders have no
write path of their own: create, replace, delete, confirm, close and reopen are the shared methods, each
wholly inside `SerializedPerTenantAsync`. Create, replace and delete of a stock document, posting and
reversal run inside it as before, and the order a posting or reversal changes is read and written there.
Consequences that hold for 010: a close cannot fall between a delivery's check and its save; two deliveries
cannot both see the same outstanding quantity or the same stock; `SO-` numbers have no gap.
`open-items.md` is updated: 005/2 is done for every MVP spec.

**Tenant scope.** `SalesOrder` and `SalesOrderLine` are `ITenantOwned` through the shared base types, so
filtered and stamped like purchase orders. Every new foreign key includes `TenantId` and restricts deletes:
order to partner, warehouse and the four API-key columns; line to order, article and unit; stock document to
sales order; stock document line to sales order line. The reserved quantity is read through the filtered
sets (T2). No `IgnoreQueryFilters()` was added; the only one is still the API-key lookup. One migration.

**Layers.** Rules are in Domain (`Order`, `OrderProgress`, `OrderSide.FulfilledBy`, `StockAvailability`,
`StockDocument`) and Application (`OrderOperations`, `OrderValidation`, `OrderLinkChecks`,
`StockDocumentValidation`). `SalesOrderEndpoints` and `OrderEndpoints` bind, call and map; the eight sales
tools resolve `SalesOrderOperations` only.

**MCP.** Eight tools added; the unit test counts 53. The texts section 5 asks for are there:
`sales_order_create` (a draft is an offer and reserves nothing; selling price without tax; `isCustomer`),
`sales_order_confirm` (permanent; reserves; not refused when stock is short; `availableQuantity`),
`sales_order_get` (how to deliver), `stock_document_post` (a delivery can fail with `INSUFFICIENT_STOCK`
although the order is confirmed; an unlinked issue can take reserved stock), `stock_on_hand_list` (four
quantities), and the further `IN_USE` case on the delete tools of the masters.

   rule in SQL (`BaseQuantity − fulfilled` over lines of `confirmed` orders), as it must to page in the
   database; so AC-03's unit test of R15 tests the Domain statement and the tester's AC-75–AC-79 test the
   query. Both are right today. Open item 010/1, after MVP.
2. **Order lines are still judged with `StockDocumentType.Receipt`** passed to `StockLineChecks.References`
   and `Convert` in the shared `OrderOperations` (review 009, non-blocking 3). Correct for both kinds — a
   quantity above zero that converts — and commented; the argument is still named for a stock document type.
   With 010/1.
3. **"At most one order link" is enforced in Domain and validation, not by a database check.** As with
   every other document invariant; belongs with open item 005/4.
4. `GET /sales-orders/{id}` of a draft and the order list inherit open items 007/1 and 009/1 through the
   shared code; nothing new.
5. The stock-on-hand query is now a three-way `Concat` over a projected class. It cannot be judged without
   running it against PostgreSQL; the tester's AC-75–AC-78 and spec 009's AC-75–AC-77 exercise it, so the
   required green run settles it.
