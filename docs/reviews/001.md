# Review 001 — spec 001, foundation + units of measure

Reviewed: `git diff main...feat/001-foundation-uom` at commit `1eda78f` (branch commits `718d630`, `91d1763`,
`1eda78f`), against `docs/specs/001-foundation-uom.md`, `docs/architecture.md` and ADR-0001 … ADR-0006.
Reviewer: architect, 2026-10-09.

The implementation is of high quality and one small step from OK. Two changes are required. The first is a
defect found by running the service (a client can produce `500`); the second follows from the answer to the
builder's question Q5. Both needed a spec amendment, which is made in the same commit as this review
(spec 001: R4, R9, R15, R16, AC-47, AC-58, AC-59, AC-72, AC-73). Neither is a case of the builder ignoring the
spec as it was written.

## Required changes

1. **A NUL character in `name` or `search` produces `500 INTERNAL_ERROR`.** Reproduced against
   `docker compose up` of `1eda78f`:
   - `POST /api/v1/units-of-measure` `{"code":"nul","name":"a\u0000b"}` -> `500`
   - `PUT /api/v1/units-of-measure/{id}` with the same `name` -> `500`
   - `POST /api/v1/admin/tenants` `{"code":"nul-t","name":"a\u0000b"}` -> `500`
   - `GET /api/v1/units-of-measure?search=a%00b` -> `500`

   PostgreSQL rejects U+0000 in text (`22021 invalid byte sequence for encoding "UTF8": 0x00`), and nothing
   validates it earlier. Every such request also writes an error with a stack trace to the log. Other control
   characters (`"a\u0007\nb"`) are stored as part of a name.
   Required: implement the amended rules — spec 001 **R4** (a name contains no control characters), **R9**
   (neither does `search`), **R16** (no input-triggered `500`) — in the Domain/Application layer
   (`NameRules`, list validation), with tests for **AC-47** and **AC-58**. The rule must cover tenant name,
   unit name on create and replace, and `search`.

2. **Unknown query parameters are silently ignored.** `GET /api/v1/units-of-measure?serach=kg` returns the
   unfiltered list. For request bodies the spec rejects unknown properties precisely so that a typo is an error
   (R10); the builder asked what applies to query strings (Q5) and built "ignored". The answer is "rejected"
   (`docs/questions/001-q.md`, Q5), now spec 001 **R15**: any query parameter an operation does not define, on
   any `/api/v1` route, -> `400 VALIDATION_FAILED` with `errors` keyed by the parameter's name; names are
   case-sensitive (`?Limit=1` is unknown).
   Required: implement R15 and add tests for **AC-59**. The existing test
   `T1_No_query_parameter_or_header_selects_a_tenant` asserts the old behaviour for `?tenantId=` / `?tenant=`
   and must be changed to expect `400` for the query-parameter part (the header part stays: headers are
   ignored). This is a change of a test because the spec changed, and is explicitly approved here.

Also add tests for **AC-72** and **AC-73**. The behaviour is already as specified (confirmed in Q1 and Q4);
`AC71_Method_not_supported_on_a_known_path_is_a_problem_too` currently accepts `404` or `405` and should be
tightened to `404` with code `NOT_FOUND`.

## What was checked and found correct

Acceptance criteria. Every non-manual criterion has at least one named test that asserts what the criterion
says (status, `code`, `errors` keys — never message text): AC-03…05 (`ArchitectureTests`), AC-06, AC-07
(`StructureTests`), AC-10…22 (`AuthenticationTests`), AC-30…46 (`UnitOfMeasureTests`), AC-50…57
(`UnitOfMeasureListTests`), AC-60…67 (`TenantIsolationTests`), AC-70, AC-71 (`ErrorModelTests`). Many go beyond
the criterion (concurrent tenant creation, raw-SQL checks that the database itself rejects a duplicate code and
a dangling tenant, a DbContext without a tenant sees and writes nothing).
- AC-01: taken from the orchestrator's independent run on `1eda78f` — 68 unit + 133 integration tests passed,
  0 failed, 0 skipped. `scripts/dotnet.sh` runs the SDK container with the host uid/gid, so no root-owned files.
- AC-02: by inspection — one `Xerp.slnx`, the six projects, no `api/`.
- AC-08: verified by the reviewer — `docker compose up --build` of an export of `1eda78f` (separate project
  name, port 18001, `XERP_ADMIN_KEY` set): `/health` `200`; tenant created with `curl`; unit created and listed
  with the returned key. The database port is not published.

Tests were not weakened. The test commit `91d1763` precedes the implementation commit `1eda78f`; the only test
change in the latter is one line in `XerpFixture` (Testcontainers builder API). No skipped tests, no conditional
compilation.

Tenant scoping. The global query filter is applied by type to every `ITenantOwned` entity; the DbContext stamps
`TenantId` on insert and refuses added/modified/deleted rows of another tenant, and refuses any write without a
tenant; a context without a tenant reads nothing. The only `IgnoreQueryFilters()` is the key lookup in
`ApiKeyLookup`. Unique indexes are `(TenantId, lower(Code))`; the audit foreign keys include `TenantId`. The
tenant is set once per request from the credential (`RequestActor`) and from nothing else. `WhoAmI` reads
`Tenants` (not tenant-owned) by the credential's tenant id only.

Layering. Project references and the architecture tests match the dependency table. Rules are in Domain
(`CodeRules`, `NameRules`, entities) and Application (validation, uniqueness, operations returning
`Result`/`AppError`); endpoints bind, call one operation and map. Query-string and JSON binding in `Xerp.Api` is
transport parsing, not business logic. Npgsql types do not reach Application (unique violations are translated
in the DbContext).

Security. Probed on the running service: a tenant key on `/api/v1/ADMIN/tenants`, `/api/v1/%61dmin/tenants`
and `/api/v1/x/../admin/tenants` -> `403`; on `/api/v1//admin/tenants` -> `404`; the admin key on
`/API/V1/units-of-measure` -> `403`; two `Authorization` headers -> `401`; unknown paths under `/api/v1` need a
credential before they answer `404`. Keys are stored as SHA-256 only; the admin key is compared in constant
time and ignored when shorter than 32 characters. Neither a tenant key nor the admin key appeared in the
container log; failed SQL is logged with masked parameters. Problem bodies carry no exception text. A 40 MB body
-> `400`. Case-insensitive uniqueness holds for non-ASCII letters with the image's default locale
(`Ž1` then `ž1` -> `409 CODE_TAKEN`).

## Non-blocking

1. `IXerpDb` exposes the unfiltered `Tenants` set to every Application operation. Only `WhoAmI` uses it, and
   correctly, but nothing stops a later operation from reading other tenants' rows. Prefer a narrow port
   ("the current tenant's code and name") and remove `Tenants` from `IXerpDb`; do it no later than spec 003.
2. Case-insensitivity relies on PostgreSQL `lower()`, whose handling of non-ASCII letters depends on the
   database's locale provider. It works with the `postgres:18` image default; add one test with a non-ASCII case
   pair (`Ž1` / `ž1`) so that a locale change fails a test instead of silently allowing duplicates.
3. `WhoAmIOperation` can return `UNAUTHENTICATED` (key or tenant gone between authentication and the query);
   that response goes through `Problems.From` and lacks `WWW-Authenticate: Bearer`. Set the header wherever the
   `401` is written.
4. `CredentialResolver.MaxTokenLength` (512) silently makes an admin key longer than 512 characters unusable.
   Treat such a setting as not configured and say so in the start-up warning.
5. `DbNames` puts index names into Application so that operations can recognise "their" unique violation.
   Spec 002 adds foreign-key violations to translate (ADR-0008, decision 6); consider letting Infrastructure
   translate a constraint into a meaning (which entity, which field) rather than growing a list of constraint
   names in Application.
6. The `404` written for an unsupported method keeps the `Allow: GET, POST` header set by routing. Harmless and
   mildly useful; either keep it deliberately or clear it.
7. The request body limit is Kestrel's default (30 MB). A much smaller limit for `/api/v1` (for example 1 MB)
   would be appropriate; no spec requires it yet.
