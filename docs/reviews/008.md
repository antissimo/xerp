**Open item 006/2 (before MVP): done.** `StockDocument.Reverse` no longer refuses an empty set of entries
for a count. The guard is exact there: a count is reversed with as many entries as it has lines with a
difference, none included; the other types still need at least one. Tested by the unit tests
`R17_A_posted_count_that_wrote_no_entries_is_reversed_like_any_other` and `R17_A_count_is_reversed_with_exactly_its_entries_…`
and by the tester's `AC62_Reversing_a_count_that_wrote_no_entries`.

**Open item 005/2 (per-tenant lock, before MVP): done for spec 008.** Create, replace, post and reverse all
run inside `IXerpDb.SerializedPerTenantAsync`. The book quantity is read under the lock when a count is
saved, and compared under the lock when it is posted, in the transaction that writes the differences. So
stock cannot move between the comparison and the write; the races AC-45 and AC-46 pass. Nothing slow runs
inside the lock.

**The tester's later tests (`8decf12`) — read against the code, not run.** `41d275b` would pass both.
- *A posted count without differences is reversible* (`AC62_R17_…`, and `AC81_…` through the tool). With no
  entries the reversing movements are empty, so `ReversalSufficiency` passes; `Reverse` expects zero entries
  for such a count and accepts; the reversing document gets the next `SC-` number, copies of the lines
  (the line with quantity `0` included — `CopyOfPosted` does not judge the quantity) and no entries; the
  original becomes `reversed`. A second reverse, a reverse of the reversing document, a delete and a post
  are `INVALID_STATE` by the existing checks; none of them reaches the counter.
- *An inactive warehouse is reported alone on posting a count* (`AC39_R9_…`). Posting a count goes through
  the same `StockLineChecks.ActiveForPosting` as every type, and this branch has the fix of review 006:
  articles are looked at only when no warehouse is inactive, then all inactive ones are named.
The green run on the closed tip is what proves it; this reading found nothing against it.

**Tenant scope.** No table and no entity added; `BookQuantity` is a column of the tenant-owned line. Book
quantity and current stock come from `db.StockLedgerEntries` through the global query filter, so they are
the caller's tenant's stock only (T1). The counter is per tenant. No `IgnoreQueryFilters()` in the diff.
AC-90–AC-92 pass.

**Layers.** The rules are in Domain (`CountRules`, `QuantityRules.IsValidOn`, `UnitConversion.TryToBaseOn`,
`StockMovements.OfCountLine`, `StockDocument`) and Application (`StockDocumentValidation`,
`StockLineChecks.Current`, the operations). Api changes are the status of `COUNT_OUTDATED` (`409`) and tool
text. `DifferenceQuantity` is computed, not stored, and ignored by the mapping. The DbContext guard for
posted documents covers the new column like every other.

**MCP.** Still 37 tools; `type` allows `count` on `stock_document_create` and `stock_document_list`; the
descriptions required by section 5 are there (`quantity` on a count, what a count is and when to use it,
`COUNT_OUTDATED` with the remedy, `SC-`).
